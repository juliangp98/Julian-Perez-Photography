# Julian Perez Photography

The custom marketing site for [julianperezphotography.com](https://julianperezphotography.com) — a DMV-based wedding, portrait, and event photographer. Built as a replacement for the previous Adobe Portfolio site to give Julian full control over content, SEO, booking, inquiry flow, and analytics.

## Stack

- **[Next.js 16](https://nextjs.org)** (App Router, Turbopack) on **React 19** + **TypeScript**
- **[Tailwind CSS v4](https://tailwindcss.com)** with custom CSS variables in `src/app/globals.css`
- **[Resend](https://resend.com)** for every email the site sends, and for receiving client replies onto project threads
- **[Supabase](https://supabase.com)** Postgres for the private client store (projects, message threads, settings)
- **[Twilio](https://twilio.com)** for optional SMS confirmations (skipped when its settings are unset)
- **[Groq](https://groq.com)** (or any OpenAI-compatible provider) for the optional AI features
- **[Sentry](https://sentry.io)** for error reporting
- **[Square Appointments](https://squareup.com/us/en/appointments)** embedded at `/book`
- **[Pic-Time](https://pic-time.com)** embedded at `/client`
- **Google Places API (New)** for live Google reviews, with a manual-testimonial fallback chain
- **[Sanity](https://sanity.io)** — embedded Studio at `/studio` is the runtime source of truth for journal posts, site settings, services, umbrellas, portfolios (metadata), and the About page
- **[Vercel Web Analytics](https://vercel.com/analytics)** + optional **Google Analytics 4**
- Hosted on **Vercel**

> ⚠️ This project is on Next.js 16 — APIs and conventions may differ from what's documented for Next.js 14/15. When in doubt, check `node_modules/next/dist/docs/`. See `AGENTS.md`.

## Content model

Sanity is the runtime source of truth for journal posts, site settings, services, umbrellas, portfolios, and the About page. Each getter in `src/lib/content.ts` reads Sanity first and falls back to a hard-coded default if the network fails or returns an empty result. Those defaults — in `src/lib/{site-settings,services,portfolios,about}-data.ts` — play a dual role: runtime fallback when Sanity is unreachable, and seed source when `npm run seed:sanity` populates a fresh dataset.

Portfolio binaries stay in `/public` under the Lightroom → `npm run import-photos` workflow. Sanity stores the metadata (title, slug, umbrella, description, order, hidden flag); `spliceManifest()` in `src/lib/content.ts` unions the Sanity metadata with `src/lib/portfolio-manifest.ts` at request time so the gallery gets the cover image + the full image array at no extra Sanity round-trip cost.

To add a new service:

1. Add the slug to the `ServiceSlug` union in `src/lib/types.ts`
2. Add the service entry to the `services` array in `src/lib/services-data.ts`
3. Add a matching portfolio entry to `src/lib/portfolios-data.ts`
4. Add the slug to `KNOWN_SLUGS` in `scripts/import-photos.mjs`
5. Run `npm run seed:sanity` to push the new rows into Studio

The sitemap, per-category metadata, JSON-LD, and `generateStaticParams` all derive from `getVisibleServices()` / `getVisiblePortfolios()`, so new entries flow through automatically.

## Architecture notes

### Next.js 16 gotchas

- Dynamic routes use **async `params`** — every page/route handler with `[slug]` or `[category]` destructures `await params` at the top of the function. Omitting the await is a type error in TS but a subtle render bug in JS.
- App Router only — there is no `pages/` directory.
- Dev uses **Turbopack** by default. If a package fails to resolve in dev but builds fine, check its ESM / CJS export map before chasing a Turbopack bug.
- Before writing framework-touching code, skim the relevant doc under `node_modules/next/dist/docs/`. APIs like `revalidateTag`, `revalidatePath`, and `unstable_cache` have changed between 14/15/16.

### Two-layer cache model

Every Sanity-backed read flows through **two caches**:

1. **Next Data Cache** — `next: { revalidate: 60, tags: [...] }` on every GROQ fetch. Busted by `revalidateTag(tag, { expire: 0 })`.
2. **Vercel CDN** — rendered HTML is cached at the edge with `s-maxage=60`. Busted by `revalidatePath(path)`.

`revalidateTag` alone is not enough: a page whose HTML is already in Vercel's edge cache keeps serving stale HTML until the CDN TTL expires, even if the next cold render would fetch fresh data. The webhook at `/api/sanity-webhook` calls both functions so publish → propagation lands in under a second.

### Sanity webhook

`/api/sanity-webhook` receives signed POSTs from Sanity on every publish, verifies the HMAC via `@sanity/webhook`, and invalidates both cache layers for the affected doc type. Signature verification means an attacker with the endpoint URL but without `SANITY_WEBHOOK_SECRET` can only trigger 401s, never force a revalidation. Setup details live in `sanity/README.md`.

## Importing portfolio photos

Each portfolio gallery resolves its images from the **first available source** (see the resolver in `src/lib/content.ts`): a Studio-uploaded Sanity `gallery[]`, else the Lightroom manifest, else a placeholder. The two image sources are never merged — a slug uses one or the other — so moving a gallery into Studio supersedes the manifest for that slug with no syncing. A future bespoke `/admin` uploader (Vercel Blob + Supabase) would slot in as a third source ahead of these without touching any renderer.

### Studio upload (preferred)

Open `/studio` → a Portfolio Category (e.g. "Weddings") → the **Photo gallery** field. Drag images in, drag to reorder (the first image is the cover), set alt text, and adjust the crop via hotspot. Sanity auto-generates the CDN URL, blur placeholder (LQIP), and dimensions, so the gallery grid, lightbox, the `/portfolio` index card, and the home teaser thumbnail all update live on publish — no redeploy. Storage rides the Sanity Free tier (100 GB assets + 100 GB bandwidth/month, hard-capped); the CDN serves resized derivatives, so per-view bytes stay small.

### Images in Studio (all surfaces)

The same upload pattern (native Sanity `image` field → `toSiteImage()` in `src/lib/content.ts` → `next/image`, with a graceful fallback) now backs **every** image on the site. All are optional and degrade to the prior state (manifest path or text-only) when unset:

| Where | Studio field | Fallback |
| --- | --- | --- |
| Home hero (full-bleed) | `Site Settings → Home hero photo` | text-only hero |
| Portfolio gallery | `Portfolio Category → Photo gallery` | Lightroom manifest |
| Portfolio card/teaser cover | `Portfolio Category → Cover photo` | first gallery image |
| About headshot + sidebar | `About Page → Headshot` / `Sidebar photos` | `/public/about` manifest paths |
| Service hero + card thumbnail | `Service Category → Hero photo` | text-only |
| Journal cover + inline | `Journal Post → Cover image` / body images | — (Sanity-only) |

Uploading in Studio supersedes the fallback for that surface — the two are never merged, so there's nothing to keep in sync. Everything publishes live via the webhook with no redeploy.

**Batch upload + optional details.** The gallery fields render as a grid: drop or select **several files at once** and each becomes its own item, then drag to reorder. The per-photo `alt` and `caption` are **optional** everywhere — upload a batch and publish immediately, then come back to add alt/captions whenever. When `alt` is blank the site falls back to a sensible label (the collection/page name) so the image still has meaningful alt text.

**Generate alt with AI.** To fill alt for a batch without typing it per photo, use the admin **Content tools → Portfolio image alt text** panel (`/admin/content`): pick a gallery, "Generate all" (or per-photo), review/edit, and Save. It works for both Studio-uploaded and Lightroom galleries; the saved text is stored as a Supabase override (`portfolio_image_alt`) that **wins at render** over the image's own alt and survives re-imports — no Sanity write token needed. Requires `GROQ_API_KEY` (vision) + Supabase configured.

### Lightroom export + script (fallback)

For any slug without a Studio gallery, photos are exported from Lightroom Classic into per-slug folders, then imported via a script that copies them into `public/portfolio/<slug>/` and regenerates `src/lib/portfolio-manifest.ts`. This path remains fully supported.

```bash
# Import everything from a source directory (one subfolder per slug)
npm run import-photos -- --source ~/Desktop/lightroom-export

# Import a single category
npm run import-photos -- --source ~/Desktop/lightroom-export/weddings --slug weddings

# Preview the changes without writing files
npm run import-photos -- --source ~/Desktop/lightroom-export --dry-run

# Also generate descriptive AI alt text for new/placeholder images (needs GROQ_API_KEY)
npm run import-photos -- --source ~/Desktop/lightroom-export --alt
```

A file named `cover.jpg` or `hero.jpg` (any extension) is promoted to position 0 and used as the gallery's cover image. Re-running the script picks up new or removed images without touching Sanity or the portfolio fallback data.

**Alt text.** Each image carries an `alt` string for accessibility and SEO. By default new images get a neutral `"<slug> photograph N"` placeholder; pass `--alt` (with `GROQ_API_KEY` set) to describe them with the vision model instead. Re-imports **preserve** any non-placeholder alt already in the manifest, so AI descriptions and hand edits survive. For per-image review after import, the admin **Content tools → Portfolio image alt text** panel generates, edits, and saves alt that overrides the manifest baseline (persisted in Supabase — see the `portfolio_image_alt` table below); the override wins at render and survives the next import.

## Adding wedding films

Films are Video Entries on the `wedding-films` portfolio in Sanity Studio. Optionally mirror a film into `wedding-films.videos[]` in `src/lib/portfolios-data.ts` so it keeps rendering during a Sanity outage (then `npm run seed:sanity` — note the seed is `createOrReplace`, so Studio-only entries are wiped when you re-seed). Two upload paths:

**YouTube (preferred when the music isn't blocked):** upload as Public or Unlisted with embedding allowed, then add a Video Entry (Source Kind "YouTube") and paste any URL form or the bare video ID — the renderer extracts the ID and falls back to YouTube's poster frame when the thumbnail is blank. Set `featured: true` on the film that should lead `/services/wedding-films`.

**Self-hosted on Vercel Blob (music-blocked films):**

1. Re-encode to H.264/AAC MP4 if needed (browsers won't play VP9/HEVC/AV1 from a `<video>` tag):
   ```bash
   ffmpeg -i input.mp4 -c:v libx264 -preset slow -crf 22 -c:a aac -b:a 192k -movflags +faststart output-h264.mp4
   ```
2. Upload — reads `BLOB_READ_WRITE_TOKEN` from `.env.local` and prints the public URL:
   ```bash
   npm run upload-video -- ./path/to/output-h264.mp4
   ```
3. Export a 16:9 thumbnail (~1280×720; required — Blob entries have no auto-fallback):
   ```bash
   ffmpeg -ss 00:01:30 -i ./path/to/output-h264.mp4 -vframes 1 -q:v 2 public/portfolio/wedding-films/thumbnails/<slug>.jpg
   ```
4. Add the Video Entry with Source Kind "Self-hosted (Vercel Blob)", the Blob URL, and the thumbnail path.

## Embedded third-party tools

- `**/book**` — embeds `siteSettings.bookingUrl` (Square Appointments) in an iframe. The iframe **cannot** use the `sandbox` attribute — Square detects sandboxed contexts and silently no-ops on click. A fallback "Open in new tab" button is rendered for browsers that block the embed.
- `**/client`** — embeds `siteSettings.clientGalleryUrl` (Pic-Time) the same way, with the same fallback.
- **Google Reviews** — `src/components/marketing/GoogleReviews.tsx` tries the Places API first. If the call fails or env vars are unset, it renders manual testimonials from `siteSettings.testimonials`. If both are empty, the component renders `null` so the page degrades cleanly.

## Journal (Sanity CMS)

The `/journal` section is backed by a Sanity project. The embedded Studio lives at `/studio` and is bypassed by the site's Nav/Footer so it owns the full viewport.

- **Editing**: go to `/studio`, sign in with the Sanity account that owns the project, and publish or edit any document. With `SANITY_WEBHOOK_SECRET` configured, changes appear on the site within a second of publish. Without the webhook, the site polls on the 60s revalidate window — edits still land, just slower.
- **Schemas in Studio**: `journalPost`, `siteSettings` (singleton), `categoryUmbrella` (locked set of 4), `serviceCategory` + inline `pkg`/`addOn` objects, `portfolioCategory` (metadata-only — binaries stay in `/public`), and `aboutPage` (singleton). See `sanity/README.md` for the rendering surface per schema.
- **No env vars set?** `/journal` renders a "Coming soon" placeholder, `/studio` boots Sanity's project-connect screen, and every server page falls back to hard-coded values from `src/lib/*-data.ts`. None of this breaks the build.

### Seeding site content

The first time you connect a Sanity project — or any time you update the hard-coded defaults in `src/lib/{site-settings,services,portfolios,about}-data.ts` — push them into the dataset:

```bash
# 1. Create a write token at https://sanity.io/manage → Project → API → Tokens → +Add
#    Role: Editor. Copy the value.
# 2. Paste into .env.local:
#      SANITY_API_WRITE_TOKEN=sk...
# 3. Seed:
npm run seed:sanity
# 4. DELETE the token from both .env.local and sanity.io.
#    The runtime site never reads this value — only the seed script does.
```

The seed uses `createOrReplace` at stable `_id`s, so it's idempotent. Any editor changes made in Studio **are overwritten** when you re-seed — only run this when you explicitly want the dataset to mirror the hard-coded defaults.

## Planning questionnaires

Schema-driven planning questionnaires live in `**src/lib/questionnaires.ts`**. Each questionnaire is a `Questionnaire` → `Section[]` → `Field[]` tree. Field types include `text`, `textarea`, `email`, `tel`, `date`, `time`, `number`, `select`, `radio`, `checkbox`, and `package` (the last one resolves at render-time from `services[slug].packages` so package lists never drift from pricing).

- **Routes**: `/questionnaire` is the index; `/questionnaire/[service]` renders the form for one service (statically generated per slug in `QUESTIONNAIRES`).
- **Submissions**: posted to `/api/questionnaire`, validated against the schema (skipping fields hidden by `showIf`), and emailed via Resend reusing the same env vars as `/api/inquire`. Without `RESEND_API_KEY` set, submissions log to the dev console.
- **Drafts autosave** in `localStorage` under `questionnaire-draft-{slug}` and clear on a successful submit.
- **Conditional fields** use `showIf: { id, equals }` so follow-up questions only appear when relevant.
- **Prefill via URL**: query params seed initial values, e.g.
  ```
  /questionnaire/weddings?fullName=Sarah&package=Premium&eventDate=2026-08-15
  ```
  Paste this kind of link into post-booking confirmation emails so clients land on a partly-filled form.

### Adding a new questionnaire

1. Define a `Questionnaire` constant in `src/lib/questionnaires.ts` (most use the shared `yourDetailsSection` and `bookingStatusSection(slug)` as the first two sections).
2. Register it in the `QUESTIONNAIRES` map keyed by `ServiceSlug`.
3. The service page CTA (`/services/[category]`), the index page, and the sitemap pick it up automatically. No other wiring needed.

## Testing

A Playwright end-to-end suite lives in `tests/e2e/`, covering the public pages and forms, the API guards (validation / honeypot / rate limit), accessibility scans via axe, and the admin + portal surfaces:

```bash
npm run test:e2e                              # full suite; boots the fakes and its own app server on :3100
CI=1 npm run test:e2e                         # the same against a production build, as CI runs it
npx playwright test tests/e2e/a11y.spec.ts    # a single spec file
```

The suite never reaches a real provider. `playwright.config.ts` starts `tests/e2e/support/fake-providers.mjs` (stand-ins for Resend, the AI provider and Twilio) and points the app at it, so sends, drafts and sign-in emails run their real code paths; specs read what was "sent" through the `fakes` fixture in `tests/e2e/support/fixtures.ts`, which also provides signed-in `adminRequest` / `adminPage` / `portalRequest` and a per-test client IP. The client store is a separate test Supabase project: put its keys in `.env.test` as `TEST_SUPABASE_URL` and `TEST_SUPABASE_SERVICE_ROLE_KEY` (run `supabase/schema.sql` on it once). Each run starts by clearing test records over an hour old from that project (projects on `example.com` and `.test` addresses, which every spec uses; `tests/e2e/support/reset-test-store.ts`), so the store doesn't grow without bound; specs create the records they assert on and don't need it empty. Runs share the store's AI model choice, so run one suite at a time against it. Without the keys the store stays blank and store-backed specs skip. CI (`.github/workflows/ci.yml`) runs lint, typecheck and the suite against a production build on every push and PR (locally, prefer `CI=1` for the whole suite: the dev server compiles each route on first use and can stall on a long run); the same two keys go in the repository's Actions secrets. New code paths ship with a spec alongside them (see `AGENTS.md`).

### Dependency & integration maintenance

Monthly (or before a burst of work), run the health check and apply the safe layer:

```bash
npm run deps:check     # report: outdated packages, vulnerabilities, live service checks
npm run deps:update    # apply: in-range updates, same-major framework pins, audit fix
npm run lint && npm run typecheck && npm run build && npm run test:e2e   # verify
```

The script never crosses a major version — majors are listed for a deliberate decision (read the migration notes, or ask for a full audit). It preserves the exact pins on `next` / `react` / `react-dom` / `eslint-config-next`, and reinstalls Playwright's browsers when the test runner moves (a moved runner with stale browsers fails every page-based spec with launch errors). The integration checks confirm Groq answers and still serves any pinned model, and that Sanity and Supabase answer. Security alerts between runs come from GitHub Dependabot (`.github/dependabot.yml`, security-only).

## Deployment (Vercel)

The site runs on Vercel. The domain's DNS is on Cloudflare.

1. Push to `main`. Vercel deploys through the GitHub integration.
2. Set the settings from [`docs/configuration.md`](docs/configuration.md) in **Project Settings → Environment Variables** (production and preview).
3. Connect `julianperezphotography.com` in **Project Settings → Domains**.
4. In Cloudflare, point the web records (root and `www`) at Vercel as **DNS only** (grey cloud). Proxied through Cloudflare, every request gets a Cloudflare challenge, including Sanity's and Resend's webhooks, which then fail.
5. Check after a deploy:
   - `/sitemap.xml` lists every visible service and portfolio
   - `/robots.txt` is reachable
   - The LocalBusiness JSON-LD on `/` validates in [Google's Rich Results Test](https://search.google.com/test/rich-results)
   - The `/inquire` form delivers an email to the owner
   - `/book` and `/client` iframes render and accept clicks
   - Publishing in `/studio` reaches the site in under a second (webhook wired)
   - `npm run email:check` passes

### Email and DNS

The studio address, `julian@julianperezphotography.com` (`CONTACT_EMAIL` in `src/lib/site-settings-data.ts`), is not a mailbox. Cloudflare Email Routing forwards it to the owner's Gmail, so the root domain's MX records belong to Email Routing. Resend sends from the records on the `send.` subdomain plus `resend._domainkey`, and the inbound relay uses its own `in.` subdomain. The three never share records, so each can change without touching the others. [`docs/configuration.md`](docs/configuration.md) → "Email relay setup" has the relay steps.

### Supabase keep-alive

Supabase's free tier auto-pauses a project after ~7 days without database
activity. Because the public site reads almost entirely from Sanity, Postgres
can sit idle between admin/portal sessions and drift toward a pause. A daily
Vercel Cron (`vercel.json`) hits `/api/cron/keepalive`, which runs one trivial
count against `client_records` — enough to reset the idle timer. Set
`CRON_SECRET` in the project's environment variables; Vercel sends it as a
bearer token on scheduled runs, and the route rejects anything else. On the
Hobby plan crons run once per day, which is ample margin for a 7-day window.
(Upgrading to Supabase Pro removes auto-pausing entirely and makes this
unnecessary.)

### Pre-launch checklist

- Verify the sending domain in Resend and run `npm run email:check`
- Restrict the Google Places API key to Places API (New) + the Vercel server IP range
- Confirm pricing, booking status, and contact info are current — either in Studio or in the hard-coded `src/lib/*-data.ts` defaults (re-seed if you edited the latter)

## Client portal & CRM

Inquiries and questionnaire submissions are captured as **client records** in a
free, **private Supabase Postgres** table (`client_records`) — not Sanity,
because client PII needs a private store and Sanity's private datasets are a
paid feature. Julian manages records in the **owner dashboard at `/admin`** (a
status-grouped projects overview with direct per-record editing, plus an
external-links hub) — the Supabase Table Editor stays available as a fallback
for complex JSONB edits.

**One row is one project; the email is the person.** A single client can hold
several projects at once — an engagement and a wedding, a maternity and a
newborn session, or a handful of unrelated shoots — so the portal opens to a
**menu of that person's projects**, styled like the services / galleries index
and grouped under Julian's photographic categories. Two or more related projects
can be linked into a **bundle** (e.g. "Wedding + Engagement") by either Julian
(from the admin project page) or the client (from their menu); bundled projects
render together in their own accent-bordered group, labelled and tagged so the
relationship is obvious at a glance. Clicking a project opens its detail view —
status, dates, locations, plan, links and files (the proposal, contract,
invoice, highlights and gallery links Julian adds, plus anything the client
uploads), how they're paying, and the project's message thread (see "Client
messages" below). There the client can make limited edits, upload
files, write to the owner, and open the matching planning questionnaire
prefilled with their details.

The admin area is gated by a magic link to `ADMIN_EMAIL` (same mechanism as the
client portal, owner-only). Sign in at `/admin` with that email.

How the pieces fit:

- **Capture:** `/api/inquire` upserts a record (matched by email **+ service**,
so a second service for the same person opens a second project rather than
overwriting the first; status `new-inquiry`); `/api/questionnaire` attaches the
answers snapshot to the matching project, stores the generated plan PDF to Blob,
links it, and moves a booked project on to `planning` (a prospect keeps their
place). Both are fire-and-forget and
**no-op when the store isn't configured**, so the email flow is never affected.
- **Privacy boundary:** the app reaches the table only through
`src/lib/clients.ts` (server-only, service-role key). The portal reads via
the client projection — `internal_notes`, the budget, status history, and
inquiry context are never selected, so they can't reach a client. The
questionnaire answers are held out of the project list and added on a single
project's page: the client's own in full, and for a second photographer only
the ones about the shoot. A second photographer with read access gets a
narrower projection: no package, payment method, proposal, contract, invoice or
gallery link. The
table has Row-Level Security enabled (the service role bypasses it
server-side; nothing else can read it).
- **Auth & ownership:** magic link. The client enters their email at `/portal`,
`/api/portal/request-link` emails a one-time signed link (20-min TTL), and
`/portal/verify` sets an httpOnly session cookie carrying the **email** (the
person), not a single record id. A Next.js 16 Proxy (`src/proxy.ts`, Node.js
runtime) gates `/portal/`* and `/admin/`*. Every project read or write resolves
the row by **(project id +
session email)** — a project the URL names but the signed-in person doesn't own
returns not-found — so listing and linking projects can never reach across
people (no IDOR). Bundle writes apply the same gate: any project id not owned by
the requester is dropped, and a bundle can never span two clients. Tokens +
cookies are signed with `AUTH_SECRET` via `jose`.

### One-time setup

1. **Create a free Supabase project** at [supabase.com](https://supabase.com).
2. **Create the tables**: Supabase → SQL Editor → paste and run
   [`supabase/schema.sql`](supabase/schema.sql). It is idempotent, so the same
   file brings an older table up to date and sets up the separate test project.
3. **Copy the keys.** The dashboard's green **Connect** button surfaces both,
  or use Project Settings (gear, bottom-left):
  - **Project URL** (`SUPABASE_URL`) — Settings → **Data API** (e.g.
  `https://<ref>.supabase.co`).
  - **Secret key** (`SUPABASE_SERVICE_ROLE_KEY`) — Settings → **API Keys**.
  Newer projects show a **Secret** key (`sb_secret_…`); older ones have it
  under the **Legacy API keys** tab as `**service_role`** (the long `eyJ…`
  JWT). Either works — it's the full-access backend key. **Not** the
  `anon` / publishable key.
4. **Generate the sign-in secret.** This is not a Supabase value: run
   `openssl rand -hex 32` and use the output as `AUTH_SECRET`.
5. **Set the admin email** — `ADMIN_EMAIL=you@example.com` (the address you'll
  sign into `/admin` with; comma-separate for more than one owner).
6. Add `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `AUTH_SECRET`, and
  `ADMIN_EMAIL` to `.env.local` and to Vercel → Environment Variables (server
   scope; **no** `NEXT_PUBLIC_` prefix on any of them).

After setting the env vars, restart `npm run dev`, submit a test inquiry on
`/inquire`, then sign in at `/admin` with your `ADMIN_EMAIL` and confirm the
record shows up in the Projects overview. Until these settings are set, capture
and the portal stay off and the rest of the site is unaffected.

## Client messages

Every email the site sends a client, and every reply, lives on the project's thread: the **Messages** section of `/admin/projects/[id]`, and the same thread (minus anything held for review) in the client's portal. Every send goes through `sendEmail()` in `src/lib/email/send.ts`. Inbound mail and delivery events arrive at `/api/email/webhook` and are handled in `src/lib/email/relay.ts`; `src/lib/messages.ts` reads and writes the threads (`client_messages`).

- **Sending.** A send on a project uses the reply address `reply+<token>@<RESEND_INBOUND_DOMAIN>`, so replies come back to the site. Emails composed in the admin also BCC the owner. Each send records Resend's id. Delivery, bounce and spam-complaint events update the message, and a bounce emails the owner. A daily check settles any message whose event never arrived.
- **Replies.** A client's reply is filed on the thread and forwarded to the studio address, `julian@julianperezphotography.com`, which Cloudflare Email Routing delivers to the owner's Gmail. The forward carries the reply address as Reply-To, so answering from Gmail goes back through the site and reaches the client from the studio address, on the thread. The owner's reply is relayed only when its DKIM signature checks out; otherwise it waits on the thread for a one-click send. Mail from an address not on the project is held for review and never reaches the client. Out-of-office replies are filed and go nowhere.
- **Portal.** Clients read the thread and write on it from their project page. Collaborators don't see it.
- **History.** `npm run messages:backfill` (dry run, then `-- --apply`) files past sends from Resend's log, as far back as Resend keeps them. For mail that only exists in Gmail, forward it to the filing address shown under the project's thread (`log+<token>@...`). It is filed with its original sender and date, and nothing is sent.

Setup is in [`docs/configuration.md`](docs/configuration.md) → "Email relay setup". Run `supabase/schema.sql` first: it creates `client_messages`. Until `RESEND_INBOUND_DOMAIN` is set, sends are still recorded on the thread and replies go straight to the owner's inbox.

## AI features (admin drafting and public concierge)

Every AI feature runs on one setting, `GROQ_API_KEY` (server scope, never `NEXT_PUBLIC_`). Create a free key at [console.groq.com](https://console.groq.com). Groq is the default because its API doesn't train on what it receives, which is what makes prompts with client details acceptable. Any OpenAI-compatible provider works through `AI_BASE_URL`; keep to providers that don't train on prompts for the drafting tools. Without a key, admin panels hide their AI buttons and the public chat points to the FAQ.

**Models choose themselves.** `src/lib/ai/models.ts` reads Groq's live catalogue, ranks models by family, and test-calls one before adopting it. The fallback comes from a different family, so one retirement wave can't take out both, and the vision model must pass an image test. The choice is stored in `app_settings`. The daily cron re-checks it and emails the owner when it changes, and a call to a retired model falls through to the fallback, then to a fresh pick. `AI_MODEL`, `AI_FALLBACK_MODEL` and `AI_VISION_MODEL` are optional pins that win while the provider still serves them.

Groq's free tier has a tokens-per-minute ceiling. The public concierge uses the most, so its knowledge base (`src/lib/ai/concierge-kb.ts`) stays under a character budget. Heavier use needs Groq's Dev Tier or another provider through `AI_BASE_URL`. More design detail is in `CHANGELOG.md`.

- **Discovery calls.** A project's Call tab (`?tab=call`) holds the call guide for its kind of shoot (`src/lib/discovery-guides.ts`, six families on one shared framework), an answer box under each question and free notes, all autosaved, a date check against booked and held projects, and, with AI, the guide fitted to the client and a summary drafted from the notes. Saving the summary marks the call held and sets a follow-up to send the recap.
- **Admin drafting.** Client email is drafted in one place: the compose panel on `/admin/projects/[id]` (`/api/admin/draft-email`). It turns a pipeline template and the project's client-safe facts into a draft for review. The AI never sends, never sees the internal note, the budget or the client's email and phone, and writes `[brackets]` instead of guessing. The brand voice lives in `src/lib/ai/ai-voice.ts`. The drafter also reads the owner's three most recent substantial emails to other clients (`src/lib/ai/voice-samples.ts`), with names, addresses, links and phone numbers redacted, and matches their wording and sign-off but none of their facts. An edited draft is stored as sent, so each edit teaches the next draft. Triage and the suggested next step open this panel on a template instead of writing their own email. Every new inquiry is assessed on arrival (fit, urgency, a summary, capped at 8 seconds and skipped on any failure) and the assessment is saved on the project, and the owner email links straight to this panel to draft the reply, steered by it; set `INQUIRY_SMS_TO` for a text about the leads worth one. The assessment, the shoot brief, the plan-summary draft and the discovery-call tools share one route (`/api/admin/ai`, by `kind`) and one context builder (`src/lib/ai/project-context.ts`) with a client tier and an internal tier. The same key powers journal and page copy, portfolio alt text, and admin search. A model that's still rate-limiting after retries hands the call to the fallback model.
- **Public concierge and FAQ.** `/faq` is a searchable directory built from one source (`src/lib/faq.ts`: a general set plus every visible service's `faqs[]`). It works without AI and emits `FAQPage` JSON-LD. The same source grounds the "Ask" chat (`POST /api/concierge`), which reads public content only, refuses to invent prices or follow instructions inside visitor messages, and is rate-limited and honeypotted like the inquiry route.

## Security

sanitization, origin checks, rate limiting) are enforced in the app itself.

outside the codebase — are tracked in `SECURITY.md` at the repo root. Walk
through that checklist whenever an integration is added, a credential is
suspected of being exposed, or on a quarterly cadence.
