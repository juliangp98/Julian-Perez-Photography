# Changelog

A subsystem-level overview of what's been built. Organized by area rather than date — the history is in git.

## Site scaffold

Next.js 16 + React 19 + Tailwind CSS v4, deployed to Vercel. App Router with per-route SSG where possible; dynamic API routes on the Node runtime. LocalBusiness JSON-LD is wired into the root layout from `siteSettings` so the `<head>` of every page carries structured data. `robots.ts` and `sitemap.ts` are auto-derived from the visible service + portfolio getters.

A tab-style **section sub-nav** (`SubNav`) sits above the page title on every page in the public page groups, mirroring the admin sub-nav's look (uppercase tracking, a bottom rule) with the active tab matched by pathname and rendered in the gold accent. The **About Julian | Journal** group spans the about page and every journal post (a post highlights _Journal_), and the top-level **Portfolio** and **Services & Pricing** indexes link across to each other. A **category detail page**, though, scopes its tabs to that one category: `/portfolio/weddings` and `/services/weddings` share a "Weddings portfolio | Weddings pricing" pair (the sibling tab appears only when that sibling is published) plus an inline **back link** up to the index, set off from the tabs by a thin divider. That single affordance supersedes both the old per-page "← back" link and the old top-right "view pricing / view portfolio" cross-link, so each category offers exactly one way to switch facets and one way back. Two action groups round it out: the **booking funnel** — Inquire | Plan your session | Book | FAQ — spans `/inquire`, the planning questionnaire, `/book`, and the FAQ directory; the **client surfaces** — Client portal | Client galleries — sit on the portal and the galleries page. "Plan your session" lives only in the funnel, so no page belongs to two bars; the portal's project pages link to the questionnaire contextually instead. The same `SubNav` also powers the authenticated portals — the admin and client areas both render it with an integrated **Sign out** (its `logoutAction`), so there's one nav component site-wide and the two portals read identically. The main nav's Clients dropdown carries the Client portal link. The portal sign-in page (`/portal`) carries the client bar and forwards an already-signed-in visitor on (to their dashboard from the tab) so its "Client portal" tab resolves from either state; the `/admin` sign-in page stays tab-free. Every sub-nav-bearing page shares one wide nav region (a `max-w-7xl` row at a uniform `py-20` top offset — public, portal, and admin alike, so the bar sits at the same height everywhere) with narrower content — a login form, a questionnaire — inner-wrapped beneath it, so the rule's length and vertical position match on every page.

Three content pages put their secondary panel in a **sticky second column** on desktop, collapsing to one column on mobile: `/inquire` pins the "already booked?" planning callout beside the form, `/faq` pins the concierge chat beside the searchable directory, and `/about` pins a photo column beside the bio. The about photos are path-based like the portfolio galleries — a source `about/` folder runs through the import script into `public/about/` and a generated `about-manifest.ts` the about page merges — so adding them is one command, and the column simply doesn't render until they exist. And `/faq` no longer yanks the viewport down to the chat on load: the concierge scrolls its own log container, not the page.

Page-ending calls to action share one **`CalloutCard`** — an accent-bordered white card with an optional uppercase eyebrow, a serif title, an optional description, and pill action buttons, modeled on the service pages' "Booked or seriously considering?" box. The loose button clusters and differently-styled boxes that used to live on `/about`, `/client`, `/inquire`, `/book`, the portal sign-in page, and the services + questionnaire indexes now all render through it (the old top-right "View Services / Portfolios" index cross-links are retired in favor of the section nav), so every CTA reads as one UI.

Every button on the site comes from one **`Button`** primitive. With `href` it renders a link (an anchor when external); without, a real `<button>` that takes the usual button props plus `loading` and `loadingLabel`, which disable it and swap the label while a request runs. It owns the variants (primary, secondary, ghost, danger, and a quiet underlined `text` action) and the size scale (sm, md, lg), so padding and hover states can't drift between pages. Form submits, AI actions, the danger zone and the small inline actions all render through it.

Color comes from six theme tokens in `globals.css`: `--background`, `--foreground`, `--muted`, `--accent`, `--border`, and `--danger`, which replaced the hard-coded reds. Each is exposed as a Tailwind theme color, so components write `text-muted` or `border-danger` rather than `text-[var(--muted)]`. `Badge` holds the one set of status colors (good, warn, bad, muted) used for fit and urgency reads. Emails, the PDFs, the global error page and the image scrim render outside the site's CSS and keep their own literal colors.

The App Router has no `loading.tsx` boundaries. On Next 16.2 any loading boundary above a page made `router.refresh()` fetch the updated page after an action and then, in roughly a third of runs, never show it: a sent email, a released reply or a new collaborator stayed invisible until a reload. Measured on the admin project page against a production build, the refresh landed 30 times out of 30 with no boundary and about 7 in 10 with one at the root, in the sections, or under admin alone. Navigations to a page that waits on data keep the current page up until the next one is ready, which is Next's default. The line-art camera loading screen that the root boundary used to show is gone with it; actions confirm themselves with a `FormStatus` line rather than relying on the refreshed page.

## Project structure & conventions

`src/components/` is organized by domain. **`ui/`** holds the generic primitives: `Button`, `Panel`, `CalloutCard`, `RailCard`, `Badge`, `FormStatus`, `CopyButton`, `CopyField`, `SubNav`, `SafeImage`, `ImageScrim`, and the `fields/` form controls. **`forms/`** holds the forms (inquiry, the questionnaire with its `questionnaire/` renderer internals, `NewProjectForm`, `AssistedTextarea`). **`admin/`** holds the owner-dashboard pieces, with the AI tools grouped under `admin/ai/` around one `useAiAction` hook. **`messages/`** holds the project thread (`MessageThread`, `PortalMessageBox`, `ReleaseHeldReply`), shared by the admin and the portal. **`portal/`** holds the client-portal pieces, and **`marketing/`** the public site chrome and content components (the nav with its `nav/` menu internals, footer, galleries, concierge, FAQ browser). `src/lib/` keeps the data/content modules flat and clusters the rest: **`lib/email/`** (the sender, pipeline templates, branded layouts, inbound parsing, the relay, notifications), **`lib/ai/`** (model client, model selection, voice, voice samples, concierge knowledge base), and **`lib/pdf/`** (the printable plan documents).

Repeated UI resolves to one source. Every form control renders through the `fields/` primitives on the shared `Field` chrome. Every dropdown is **`ui/fields/Select`**, the site's one `<select>`: `SelectField` wraps it with a label (options as plain strings or value/label pairs, a placeholder option that locks for required choices or stays selectable for clearable ones, and a trailing slot for a conditional "other" input), and compact tool bars and filters use it bare with a `density="compact"` prop. The styling constants live beside them: `inputClass` / `controlClass` / `labelClass` for full-size controls and `compactInputClass` for dense tool rows (the project page's status select, the list filter bar, the portal upload row). The line under a form after an action is **`FormStatus`** (a quiet confirmation, or an error read out to screen readers), and every copy action is **`CopyButton`**, which says "Copied" for a moment. Content boxes are three cards: **`Panel`** (the white box, with a default, accent or danger `tone`), `CalloutCard` (a closing call to action) and `RailCard` (a labeled rail module), both built on `Panel`. Service nouns, `titleCaseSlug`, the review stars, the day-difference helper, the compose tokens and the date stamp each live in one place. The one human-readable date formatter is `formatHumanDate` in `src/lib/field-format.ts` — "June 7, 2026", or "Jun 7, 2026" with the short month for email subjects — shared by the journal, the portal and admin pages, and the email pipeline — joined by `formatRelativeDays` ("3 days ago") and a `STUDIO_TIME_ZONE` pin for displaying stored timestamps. Record-field display labels (source, admin status titles, document types, uploader names) live in `src/lib/labels.ts`, so a stored slug never reaches the screen; conversions with an existing domain home stay there (service titles in `services-data.ts`, referral labels in `referral.ts`, client-facing status phrasing in `client-status.ts`).

The largest components are split into focused units that their shells compose: the questionnaire's per-field rendering (`FieldRenderer`), uploads (`FileField`), and referral dropdown live in `forms/questionnaire/`; the admin form's venue/address list is `admin/AdminLocationsEditor`; and the nav's menu data, hover panels, and mobile drawer live in `marketing/nav/`, so the desktop megamenus and the mobile drawer read from one menu definition.

## Form fields & formatting

Every form on the site — the inquiry form, the multi-section questionnaire, the admin edit form, portal edits, and the new-project form — runs its inputs through one set of shared field primitives (`src/components/ui/fields/`) rather than hand-rolled `<input>`s, so formatting, validation, and the label / required-marker / inline-error chrome read identically everywhere (all off one `Field` wrapper + `inputClass`, with the helpers in `src/lib/field-format.ts`). **`PhoneField`** masks to `(703) 555-1234` as you type — the visual companion to `normalizeE164`'s server-side E.164 pass; **`EmailField`** flags an invalid address on blur and offers a one-click fix for a common domain typo ("Did you mean name@gmail.com?"); **`BudgetField`** drops in a `$` and comma-groups a plain number; **`NumberField`** holds to non-negative integers; and **`DateField`** types as `MM/DD/YYYY` (auto-slashing, auto-advancing month→day→year) and opens a **react-day-picker** calendar styled as a callout-card popover — with month + year dropdowns (a far-out date is one click, not a dozen arrow taps) and the selected day ringed in the brand accent — while storing ISO `yyyy-MM-dd`.

**Address & venue autocomplete.** `LocationField` queries `/api/places/autocomplete`, a server proxy for Google Places (New) that reuses the existing `GOOGLE_PLACES_API_KEY` (the reviews key), builds lightweight predictions from each suggestion's `structuredFormat` (no Place Details call, so no extra per-select billing), is rate-limited, and **returns an empty list when the key is unset** so the field cleanly degrades to free text. As the user types (≥3 chars, debounced) a keyboard-navigable combobox of addresses/venues drops in; selecting one fills the field, and **free text is always retained** for custom entries. It powers the inquiry "location", the questionnaire venue/address fields (`venueName` / `venueAddress` / get-ready / reception), and a new editable **Locations** section on the admin project form — a repeatable label/address/notes list persisted to the `locations` JSONB through `/api/admin/update`.

## Inquiry form + email

`/inquire` posts to `/api/inquire`. Resend sends the owner a structured inquiry email plus an auto-reply to the client. The handler writes the inquiry subject line with the event date formatted as `"Aug 15, 2027"`. The form marks its required fields — name, email, service, and the message — with an asterisk and validates them client-side on submit: a missing or malformed field shows an inline, `aria-describedby`-wired error and focuses the first offender instead of bouncing off a generic server message.

**Every transactional email shares one branded layout.** The inquiry + auto-reply, questionnaire submissions, the portal and admin magic-link sign-in links, and the client-update notification to Julian all render through `BrandedEmailLayout` in `src/lib/email/email-templates.tsx` (React Email → HTML via `render()`, with a plain-text fallback always included) — so the login links and notifications match the inquiry/questionnaire look (serif header, accent rule, footer with contact + socials) instead of ad-hoc inline HTML. Reusable content templates: `MagicLinkEmailTemplate` (portal/admin sign-in) and `NotificationEmailTemplate` (generic heading + lines + optional CTA, ready for the planned client/admin notifications). Every send draws its `from` from one `resendFrom()` helper (`src/lib/email/email-helpers.ts`) that defaults to the studio's own domain (`noreply@julianperezphotography.com`, overridable via `RESEND_FROM`) instead of the shared `resend.dev` sandbox sender, and each client-facing message carries a `replyTo` pointed at Julian's real inbox — so replies reach him without a domain mailbox to host while sending stays on the verified domain. `resendFrom()` warns loudly if it ever resolves to the `onboarding@resend.dev` sandbox sender, which silently delivers only to the Resend account's own address (every other recipient is 403-rejected) — so a stray `RESEND_FROM` override can't quietly break client mail.

**New inquiries arrive assessed.** `/api/inquire` runs the same AI assessment as the admin's "Assess this inquiry" button (`assessInquiry` in `src/lib/ai/assess-inquiry.ts`) on every submission: it starts alongside the content fetches and the client-record write, waits at most 8 seconds, and settles to nothing on any failure (Sentry `stage: "triage"`, warning level), so it can enrich the owner email but never fail or stall a submission. With an assessment, the owner email opens with the verdict ("Good fit, high urgency"), the summary and the reasons, its preheader leads with the verdict, and the plain-text part carries the same. The assessment is saved on the project (`ai_results`, see "AI-assisted drafting"), so the project page shows it without asking the AI again. A repeat inquiry from the same person for the same service keeps the project's first message, so its assessment reaches the owner email but doesn't replace the project's saved one. It writes no reply: the email's **Draft a reply** button opens the project page with Compose on the inquiry-reply template (`draftReplyHref` in `src/lib/triage.ts`, which the admin panel's link uses too), and the page steers the draft from the saved summary and key details. No client detail rides in the link's address, so none lands in browser history or request logs. The client record is filed before the owner email so the button has a project to open, which also keeps an inquiry whose email fails. The prompt treats the client's message as material to assess, never as instructions, since it runs on public input.

**Lead sources name the group, venue or vendor.** The shared "How did you hear about me?" dropdown (`src/lib/referral.ts`, used by the inquiry form and every questionnaire) has separate **Facebook group**, **Venue** and **Planner or another vendor** options. Options that point at a specific source carry a `detail` prompt ("Which group?", "Which venue?", "Which vendor?", and "Other"'s "Tell me more"), which reveals a labelled companion input; changing the choice clears it, so a venue name can't ride along under another channel. The detail travels as `referralOther` and `formatReferral` folds it in only for options that ask for it, so the owner email and the client record read "Venue: Foxchase Manor" while the subject keeps the short tag (`[via: Venue]`) for inbox filtering. A blank source is stored empty, so tallies over the records count only real answers.

Honeypot + in-memory per-IP rate limiting (`src/lib/request-guard.ts`) guard against basic abuse — 5 submissions per 10 minutes per IP, keyed per endpoint so the inquiry form and questionnaire limiters don't share a bucket.

When `RESEND_API_KEY` is unset the handler logs the payload and returns `{ ok: true, dev: true }` so local development works without a Resend account.

## SMS confirmations (optional)

When all three `TWILIO_ACCOUNT_SID` / `TWILIO_AUTH_TOKEN` / `TWILIO_PHONE_FROM` env vars are set, `/api/inquire` also dispatches a Twilio SMS confirmation. Strictly additive to the email flow: SMS is wrapped in try/catch so a Twilio failure never surfaces into the user-facing response.

Setting `INQUIRY_SMS_TO` (the owner's own number) adds an **owner text** for the inquiries worth an interruption: `shouldAlertOwner` passes a good fit, or a high-urgency lead that isn't a clear mismatch, and every inquiry when no assessment came back, since nothing then rules the lead out. The text names the client, service, date and channel, the verdict, and a summary trimmed to the 320-character cap, and points to the inbox. It is fire and forget like the client confirmation (Sentry `stage: "owner-sms"`, warning level). Phone-number normalization (`(703) 555-1234` → `+17035551234`) is a pragmatic DMV-focused pass — Twilio itself rejects malformed numbers server-side.

## Questionnaire system

Schema-driven planning forms at `/questionnaire/[service]`, defined by the `Questionnaire → Section → Field` tree in `src/lib/questionnaires.ts`. Field types: `text`, `textarea`, `email`, `tel`, `date`, `time`, `number`, `select`, `radio`, `checkbox`, and `package` (resolves at render-time from `services[slug].packages` so package lists never drift from pricing).

- Drafts autosave to `localStorage` and clear on successful submit.
- URL query-params prefill fields so clients can land on a partly-filled form from a post-booking email link.
- The wedding form's **sunset session time auto-defaults** to the ideal golden-hour start. Once the event date and a venue are filled in, a client-side effect calls `/api/sun`, which geocodes the venue via Places Text Search (New) (`geocodeAddress` in `src/lib/places.ts`, reusing `GOOGLE_PLACES_API_KEY`), looks up its IANA timezone (`tz-lookup`), computes the real sunset there (`suncalc`), and returns a start time ~25 min before it in the venue's own local clock. It only fills an empty field while the question is shown, so a manual choice is never overwritten, and soft-fails to no prefill whenever the venue can't be resolved.
- Conditional `showIf` branches hide/show follow-up fields; the server validates against the same schema so anything hidden on the client is also optional on the server. `showIf` matches against checkbox (array) values by membership, which lets a checked option reveal its own follow-up fields — the wedding questionnaire's "Vendors & coordination" section uses this so checking a vendor type opens a contact box for it.
- The wedding questionnaire captures photography style preference (with an "Other" free-text branch), engagement-session preferences (shown only for packages that include one), a structured **ceremony type** (religious / civil / cultural / hybrid) and **cultural-traditions** prompt, expected ceremony length, an outdoor-ceremony weather-backup plan, vendor contacts by type, and photo-sharing consent (full / none / per-channel-and-type partial). The ceremony-type and cultural questions mirror the wedding-films questionnaire so a hybrid couple sees the same questions on both forms.
- `/api/wedding-plan` renders a PDF preview of the wedding questionnaire for editor / client review.

## Site-wide settings in Sanity

Singleton `siteSettings` doc covers every field surfaced on the site (siteName, tagline, contact info, booking/client-portal URLs, social links, coverage area, payment prefs, testimonials, call-booking CTAs, Google profile URL). It also holds a **how-to-pay line per payment method** (`paymentInstructions`: card through Square, cash, Zelle, Venmo, Apple Pay): a project records which method its client is using, and that line shows under "Paying by" in their portal and is available to emails as `{{paymentInstructions}}`. A line left blank in Studio keeps its starting text. The dataset is public, so the Studio field says to add a Zelle or Venmo handle only where that's fine. Hard-coded fallback at `src/lib/site-settings-data.ts` (pure-data module with no runtime imports) plays a dual role: runtime fallback when Sanity is unreachable, and seed source for `npm run seed:sanity`.

`getSiteSettings()` in `src/lib/content.ts` merges remote values per-field over the fallback — a partial remote doc (editor cleared a field) still renders the page with the remaining fallback values. An optional `heroImage` (native Sanity `image`) drives a **full-bleed home-page hero**: when set, the photo fills the hero section with the tagline + CTAs over a localized scrim (light text/buttons); when unset, the hero stays the text-only treatment. Text-over-photo legibility everywhere (hero, portfolio cards + teaser, video tiles) runs through one `ImageScrim` primitive (`src/components/ui/ImageScrim.tsx`): a subtle gradient darkening confined to the caption edge — bottom for cards, left-on-desktop for the hero — that returns to the untouched image outside the text, with an `overlayTextClass` text-shadow carrying most of the contrast so the photo stays bright.

## Portfolios in Sanity

Portfolio metadata (title, slug, umbrella, description, cover path, order, hidden) lives in Sanity. Gallery images resolve from the first available source in `spliceManifest()` (`src/lib/content.ts`): a Studio-uploaded `gallery[]`, else the Lightroom-generated `src/lib/portfolio-manifest.ts`, else a placeholder. The two image sources are never merged — a slug uses one or the other — so uploading a gallery in Studio supersedes the manifest for that slug with no syncing, and a future bespoke uploader slots in as a third source ahead of these without touching any renderer. Every `PortfolioCategory` consumer still sees the same normalized image shape (`src`, `alt`, `width`, `height`, `blurDataURL`) — the general `SiteImage` type, produced by the shared `toSiteImage()` mapper reused across the home hero, about, portfolio, and service surfaces. An optional `cover` image lets editors pick which photo represents a collection in cards/teasers (`coverPhoto` on the resolved category), defaulting to the first gallery image when unset.

The `gallery` field is a native Sanity `image[]` rendered as a grid (`options.layout: "grid"`) so editors batch-upload — drop or select several files at once — reorder them (the first image is the cover), and crop directly in `/studio`; Sanity auto-generates the CDN URL, LQIP, and dimensions, and `galleryToImages()` maps them through `urlFor()` with a 2400px cap — the same plumbing journal images use. Studio-uploaded alt is native, so the Supabase alt-override layer applies only to manifest-sourced galleries. The `/portfolio` index cards and the home portfolio teaser, previously text-only, now render the resolved cover as a blurred-up thumbnail when a gallery has images and fall back to text otherwise.

Per-photo `alt`/`caption` are **optional** across every Studio image field (galleries, hero, cover, headshot, service, and journal), so a batch can be uploaded and published without stopping to write SEO for each. When `alt` is blank, `toSiteImage()` falls back to a caller-supplied label — the collection/page name — so a skipped photo still carries meaningful alt rather than an empty string.

15 non-hidden portfolio detail pages prerender as SSG via `generateStaticParams` → `await getVisiblePortfolios()`.

## Webhook revalidation

`/api/sanity-webhook` receives signed POSTs from Sanity on every publish, verifies the HMAC via `@sanity/webhook@4`'s `isValidSignature` against the raw request body, and invalidates **both** cache layers:

1. Next's Data Cache — `revalidateTag(tag, { expire: 0 })` on the collection tag plus any per-slug tag, so the next render refetches from Sanity.
2. Vercel's edge CDN — `revalidatePath(path)` on each route that renders the changed content, so the next request is a cold miss instead of serving `s-maxage=60` HTML.

Without the path-level call, the webhook returned 200 but the site kept serving stale HTML for up to 60s. Both calls together deliver sub-second end-to-end propagation. `siteSettings` is special-cased to `revalidatePath("/", "layout")` because the root layout reads it on every route.

Signature-verified means an attacker with just the endpoint URL can trigger 401s at worst, never force a revalidation. Unknown `_type` values 400-and-log so a new schema added in Studio without the corresponding handler update surfaces loudly in the Sanity webhook attempt log instead of silently no-op'ing.

## Wedding films service

## Wedding films portfolio

## Cross-questionnaire prefill (service bundles)

A client booking more than one service — a couple's wedding photo + film + engagement session, or a growing family's maternity → newborn → family portraits — shouldn't retype the answers two forms share. The success screen on any questionnaire offers a "Continue planning your {sibling} →" button for each other service in its **bundle group**, and the destination form arrives prefilled.

The mechanism is **intersection-based**, so it scales to any bundle with no per-pair field lists: each sibling button's URL carries exactly the answers the *target* form also asks for — the intersection of what was answered and `prefillableFieldIds(target)` (every field except file uploads, which can't ride a query string). Multi-select (checkbox) answers ride along as repeated query keys, so they round-trip in full — not just single-value fields. The receiving page turns query params into prefill (preserving arrays), so nothing else changes on the receiving side. Bundle groups are a one-line curated config (today `{weddings, wedding-films, engagements-couples}` and `{maternity, newborn, family-portraits, family-celebrations}`); adding a future bundle is adding a slug.

Beyond the post-submission cross-prefill, every applicable questionnaire now **asks about bundling in-form, consistently**. `getQuestionnaire` appends a generated **"Related sessions"** section — one checkbox listing the OTHER services in the slug's bundle group (resolved to their service titles), worded identically on every form — so a client's interest becomes a recorded answer Julian sees in the questionnaire read-out, not just a navigation link offered afterward. The bundle groups moved into `questionnaires.ts` so the same data drives both the prompt and the cross-prefill (the generated `bundleInterest` field is excluded from cross-prefill, since its options differ per service). Services with no questionnaire-backed siblings (graduation, headshots, concerts, …) never get the section, so it appears only where applicable.

What makes the carry-over actually work is a one-pass **field-ID harmonization across all 15 questionnaires**, which had drifted as they were authored in separate passes. The same concept now uses one canonical ID everywhere: partner's name (`partnerFullName`), the vibe/mood field (`vibe`), wardrobe help (`wardrobeHelp`), how-you-met (`howWeMet`), time-of-day (`timeOfDay`), pets (`pets`), and the shared wedding vendor contacts (`plannerInfo`, `venueCoordinatorInfo`) — on top of the ceremony block harmonized earlier. **Venue is unified** to a canonical `venueName` + `venueAddress` split on every form with a known event venue (weddings keeps a second "reception venue, if different"); forms that only collect pre-booking *location ideas* (`locationIdeas`) stay as-is, since that's a different question. Only the two wedding PDF plan modules hard-code field IDs, so they were updated to match; every other rename is internal to the schema. Concepts that merely *look* shared were deliberately left split — `partner` ("will they be in the photos?") is a yes/no, not a name, and weddings' `specialDances` (which dance moments to photograph) vs. the film's `musicLove` / `musicAvoid` (soundtrack taste) are genuinely different questions.

The success screen's layout was also tidied: the **"Track your project" portal CTA is the primary (dark) button** above the bundle card, and literal `→` / `—` escapes that rendered verbatim in button labels were corrected to glyphs.

## Observability (Sentry)

`@sentry/nextjs` is wired into the project per the upstream SDK's recommended layout. Four entry-points cover every runtime: `instrumentation.ts` at the project root dispatches to the server / edge configs through Next's `register()` hook and exports `onRequestError = Sentry.captureRequestError` so React Server Component + route-handler failures land in Sentry without per-route boilerplate; `instrumentation-client.ts` initializes the browser SDK and exports `onRouterTransitionStart = Sentry.captureRouterTransitionStart` so App Router navigations show up as performance spans; `sentry.server.config.ts` and `sentry.edge.config.ts` carry the runtime-specific `Sentry.init` calls. All four are no-ops when `NEXT_PUBLIC_SENTRY_DSN` (or the server-side `SENTRY_DSN`) is unset, so local dev without a DSN runs unchanged.

`next.config.ts` is wrapped in `withSentryConfig` for build-time source-map upload (gated on `SENTRY_AUTH_TOKEN` so non-CI builds skip the upload step; `widenClientFileUpload: true` covers dynamic-import chunks; maps are deleted from the deploy output after upload to defend against bundle leakage) and a same-origin tunnel route (`/monitoring/sentry`) that bypasses ad-blocker drops on client-side error reporting.

Browser-side Session Replay is enabled at 10% ambient capture + 100% on-error capture, with `maskAllText` / `maskAllInputs` / `blockAllMedia` pinned explicitly so the questionnaire / inquiry forms' real client PII can't end up in recorded sessions. The server, edge and browser configs share `sentry.shared.ts`: request bodies, headers, cookies and stack-frame local variables are dropped before an event is sent, `sendDefaultPii` is off, and traces sample at 10% in production. The browser config loads from `src/instrumentation-client.ts` (the app lives under `src/`, so that is the file Next reads), and server logs go to Sentry's Logs product (`enableLogs`).

`Sentry.captureException` calls land inside every existing API-route catch block (inquire, questionnaire, wedding-plan, wedding-films-plan, questionnaire-upload) plus the App Router error boundaries (`error.tsx`, `global-error.tsx`). Each call carries `tags: { route, stage }` so events group cleanly in the Sentry dashboard. Fire-and-forget side-effects (SMS, client confirmations) capture at `level: "warning"` to keep the primary failure dashboard signal-heavy.

A `beforeSend` hook strips request body / headers / cookies from every captured event before send, leaving only the URL and method — questionnaire and inquiry payloads carry real client PII that should never leave the project's own infrastructure.

CSP additions: `connect-src` += `*.sentry.io` + `*.ingest.sentry.io` (defensive; the same-origin tunnel route is the primary path), new `worker-src 'self' blob:` directive (Sentry's profiling features use Web Workers).

A `# Test + observability discipline` section in `AGENTS.md` codifies the standing requirement: new code paths ship with a smoke-level e2e test and Sentry instrumentation alongside the code.

## Client records & CRM

Inquiries and questionnaire submissions are now captured as durable **client records** (closing the long-standing submission-archive gap) in a free, **private Supabase Postgres** table (`client_records`). Sanity isn't used for this: client records carry PII, a private store is required, and Sanity's private datasets are a paid feature — a free Postgres table keeps the data private at no cost. Julian manages records in the owner dashboard at `/admin` (see "Owner admin dashboard"); the Supabase Table Editor remains available for complex JSONB edits.

The app reaches the table only through `src/lib/clients.ts` (server-only, Supabase service-role key). Reads use a few projections, each enforced at the query: the full row for admin/server reads; the client's projection (`safeSelect`), which omits `internal_notes`, the budget, status history, and inquiry context so they can never reach a client (the statuses in the log, with no notes or timestamps, reach portal pages only through `listStageFacts`, with the other stage facts it returns); and a narrower one for a second photographer (`collaboratorSelect`), which also leaves out the package and payment method and keeps only the links and files meant for them. The questionnaire snapshot is held out of the portal **list** the same way, but the single-project owner read (`getProjectForEmail`) layers it back on so a signed-in client can review their **own** answers — gated by project id + session email, so it never reaches the dashboard list or anyone else's project. Row-Level Security is enabled on the table; the service role bypasses it server-side and nothing else can read it. The canonical pipeline statuses live in a dependency-free `src/lib/client-status.ts` shared by the helpers and the portal. Array fields (locations, dates, documents, status history) are JSONB columns.

**One row is one project; the email identifies the person.** The email column is non-unique, so a single client can own several projects at once — an engagement and a wedding, a maternity and a newborn session, or unrelated shoots. Projects that belong together share a `bundle_id` with a denormalized `bundle_label` (see "Project bundles"). Helpers resolve a person's projects by email (`listProjectsByEmail`, `getProjectForEmail`) and gate every read/write on ownership.

Beyond inquiries and questionnaires, **projects can be created directly** on both sides. Julian creates one from `/admin/projects` (`/api/admin/create-project` → `createProjectManual`) with whatever he has — even just an email and "Not sure yet" for the service; a returning client starts one from their portal dashboard (`/api/portal/create-project`, email taken from the session, never the body). Both **warn on a duplicate** — an existing email+service project found by `findDuplicateProject` — but allow a second ("create another anyway"). Created projects expose a **completion link** that threads the project id: the admin project page surfaces a copyable client link (`/questionnaire/<service>?project=<id>&…` when the service has a questionnaire, `/inquire?project=<id>&…` when the service is undecided), and the portal's own questionnaire/inquiry links carry it too. All of them come from one builder, `projectLinks()` in `src/lib/project-links.ts`, which also backs the email tokens, so a link is built the same way wherever it appears. When that submission lands, `upsertClientFromInquiry` / `attachQuestionnaire` attach to **that exact project** — filling blanks, claiming the email/name, and setting the service if it was undecided — instead of spawning a duplicate, **but only when the project is unclaimed or its email matches the submitter**. A UUID id + the email-match guard + blanks-only fill mean a leaked link can't overwrite someone else's curated record, which keeps the project param safe on the public `/inquire` route. Net-new people with no record still begin at `/inquire` (the portal sign-in page routes them there), so it stays the single vetted front door.

Every project shows a friendly **display name** rather than the bare service slug — a custom one the client or admin set (the optional `project_name` column, editable from either side), or otherwise an auto name assembled from who + what + when, e.g. "Julian Perez's Wedding on 6/7" or "Carolyn Schook's Maternity Session on 5/9". The naming logic is a pure helper in `src/lib/project-name.ts` (`projectDisplayName` / `autoProjectName`) shared by the portal and admin. The **service** likewise reads as its catalog title everywhere (`serviceTitle` in `src/lib/services-data.ts`) rather than a raw slug, and the **package** is one canonical value — the bare tier name — across the questionnaire answer, the record, the admin picker (which no longer appends the price), and both portal displays.

The read layer tolerates schema drift: if a deploy lands before a migration's columns are added (the bundle id/label and custom project name, the payment method, the collaborator columns), the first projection that asks for them catches PostgREST's undefined-column error (SQLSTATE 42703), drops that group of columns for the rest of the process, and retries — so the portal and admin keep serving (minus those fields) instead of returning a 500. Each migration's columns are a group of their own, so one missing group never takes an established one down with it. Writes aren't covered, so a migration is applied before the code that writes its columns. An unrelated error is matched out and still surfaces. Applying the migration and restarting restores them. Project ids are UUIDs, so the id lookups (`getClientById`, `getClientFull`, `getProjectForEmail`, `getProjectForViewer`, `listProjectMessages`) answer "not found" for anything else up front: a mistyped project URL shows the page's not-found state (the API routes answer their own not-found), not a failed uuid cast and a 500.

Capture is fire-and-forget and **no-ops when the store isn't configured**, so the email flow is untouched on a deploy without the Supabase env. `/api/inquire` upserts a record (matched by normalized email **+ service type**, so a second service for the same person opens a second project instead of overwriting the first; status `new-inquiry`; never clobbers an advanced record). `/api/questionnaire` snapshots the answers onto the matching project (email + service), **syncs the structured answers it captures — package, event date, guest count, partner name — onto the record's own columns** so the portal and admin reflect what the client entered without re-keying, stores the generated plan PDF to Vercel Blob (`src/lib/blob.ts`), links it as a document, and moves a booked project on to `planning`; a prospect who fills in a questionnaire (not booked yet, or with no project before) keeps their place in the pipeline, since filling in the questionnaire isn't booking. `advanceStatus` only ever moves a project forward, and leaves a closed one (archived, lost or declined) alone: those are reopened by hand.

**Links and files** live in each project's `documents` array as typed entries: proposal, contract, invoice (with a due date and a paid date), timeline, highlights, gallery, moodboard, general, and the questionnaire PDF the site files itself. One list, `DOCUMENT_TYPES` in `src/lib/labels.ts`, holds each kind's label, who may add it (Julian, or a client too), whether a second photographer sees it, the status it moves the project to (highlights to Editing, the gallery to Delivered), and the Compose template that announces it. Every entry has an id. Adding, removing and changing an entry go through three Postgres functions (`add_document`, `remove_document`, `patch_document`, callable by the service role only), one statement each, so a client upload and an owner edit landing together can't overwrite each other. `projectLink(record, type)` returns the newest entry of a kind, or the newest unpaid one for invoices, and never a client's upload for a kind only Julian adds. Removing an entry takes it off the project; an uploaded file itself stays in Blob at its address, which the remove prompt says. Uploads from the portal and the admin share one `UploadButton` (`src/components/ui`), with the storage path and allowed file types defined once beside `DOCUMENT_TYPES`. The gallery link used to be a column of its own; the schema copies an existing one into a `gallery` entry, and removing that entry clears the old column so a later run of the schema can't bring it back. Each project also records **how the client will pay** (`payment_method`: card through Square, cash, Zelle, Venmo or Apple Pay), which the client sees. The schema adds `follow_up_at`, `follow_up_note` and `hold_until` for the follow-up and date-hold features, and a `client_last_contact` view (the client's newest received message and the owner's newest one that went out, per project) that runs under the table's row-level security.

## Client portal

A passwordless client portal at `/portal`. Magic-link auth via `jose`: `/api/portal/request-link` emails a one-time signed token (20-min TTL) through Resend with a uniform, rate-limited, anti-enumeration response; `/portal/verify` validates it, confirms at least one project exists for the email, and sets an httpOnly/Secure/SameSite session cookie carrying the **email** (the person), not a single record id. The gate is a Next.js 16 **Proxy** (`src/proxy.ts`, Node.js runtime) that protects `/portal/*` except the login + verify routes — running on the same runtime as the page renderers keeps cookie handling consistent across full-page loads and client-side navigations. Token + session signing share `AUTH_SECRET`; the pure `jose` sign/verify helpers live in `auth.ts` (used by both the proxy and the route handlers), while the `next/headers` cookie read/write helpers live in `auth-cookies.ts`. Sign-out (`/portal/logout`, `/admin/logout`) is a **`POST`** triggered by a form button, never a prefetchable `GET` link — so a link prefetch, which is always a GET, can't clear the session out from under the user.

The portal opens to a **menu of the signed-in person's projects**, styled like the services / galleries index, with cards grouped under Julian's photographic umbrellas and bundled projects pulled into their own accent-bordered group; each card carries the client's status label and, while the project is open, a compact bar of the same stages the project page tracks. `/portal/projects/[id]` renders one project via the client's projection (`safeSelect`), or the narrower `collaboratorSelect` for a second photographer. Every project is resolved by **(project id + session email)**: a URL naming someone else's project returns not-found, so listing and linking can never reach across people (no IDOR). All portal routes are Sentry-instrumented; `/portal` is disallowed in `robots.ts`.

**The project page follows the stage**, in the order a phone shows it (`PortalProjectView`): the name and the client's status label ("Reserving your date" while the agreement and retainer are out, "Booked" once the booking welcome confirms it); **Your next step**, one card saying what comes next, with a button when there's something to do (sometimes a second); the **stage tracker**, the same one the admin project page draws ("Step 3 of 9: Reserving your date" when the call was passed over, the call and the proposal left out when the project skipped them), read from `listStageFacts` (through `portalStageFacts` in `src/lib/portal-view.ts`, which also reads the emails sent on the project), which lets only the tracker's facts out of the owner-side columns and the thread; the prompt to **set up a service** when the project has none (only while it's open and before the shoot, by its date or its stage); the project's **links and files grouped by kind** (proposal, contract, invoices with their due date or that they're paid, timeline, highlights, gallery, ...); the **messages**; **Your plan** and the project facts (service, package, date, any other dates, guests, partner, a running date hold, how they're paying with its how-to-pay line, locations), the plan once the project has reached Proposal sent or later (a date being reserved counts as Booked; a closed project goes by the last stage it reached); the **planning questionnaire** callout (its prompt only while the project is open and before the shoot, by its date or its stage, the answers once sent); then the details they can edit and the **upload** (timeline, moodboard or general, since proposals, contracts, invoices and galleries are Julian's). The details form writes through `/api/portal/update`, whose zod schema is the whitelist (phone, partner name, guest count, project name); `/api/portal/upload` issues a Blob upload token only to a signed-in session, for the allowed file types up to 15 MB; `/api/portal/attach-document` links only a Vercel Blob address, under a client kind, as `uploadedBy: "client"`. Both writes re-check that the project is the signed-in person's own (`getProjectForEmail`). The next step is worked out by rules (`clientNextStep` in `src/lib/next-step.ts`, beside the owner's): book a discovery call; the proposal on its way, then ready with the date held (or in their email, when its link went in the email alone); sign the contract and pay the retainer (the invoice the contract email names, `openInvoice`) by its due day, with how to pay, or only sign while the invoice is still to come, then that the retainer is in once one is paid; Julian's contract on a lead skips straight to this, as the owner's step does, and the lead's status and tracker read Reserving your date; you're booked; fill in the prefilled questionnaire, then book the call that plans the day (`planningCallFor`: the wedding timeline call for weddings and films, the planning call otherwise, the same one the questionnaire's thank-you page offers first, then the other calls that fit, `thankYouCalls`), then the timeline once Julian adds it; a project the questionnaire moved past Booked before the booking was done (Julian's contract and invoice on it, or either one while it last stood at Booked, none paid, no booking welcome sent, and not last standing at Contract signed, which confirms a booking set by hand until it's set back) keeps asking for both, in Planning and in Scheduled up to the shoot (the projects the owner's step sends back to the booking), and its status and tracker stay at Reserving your date meanwhile (`stillReserving`, built on the same booking test); a shoot already past moves the step on to editing, the status to Captured and the tracker to Editing, whatever the planning left (`shootPassed`, which also turns the owner's step at Contract signed or Planning to the thank-you); the week of the shoot, a project at Contract signed reads as the shoot itself, as does a planning project the day before or the day of; the shoot today, tomorrow, on Saturday or on its date, with the timeline and a pointer to the plan when there is one; the highlights; the gallery and any open invoice; a review, with any invoice still open kept on the card. A closed project shows none. The six-milestone timeline it replaces is gone.

**The path to it** keeps the client where they were going: the page they were sent to sign in from is carried in the magic link (`next`, only the projects list or one project's page, `portalReturnPath` in `src/lib/auth.ts`) and opened after signing in (a link that ran out, such as an invite opened the next day, keeps its page for the fresh one, `expiredMagicReturnPath`, which takes it only from a link the site signed; a visitor already signed in who reaches `/portal` with a page to return to goes straight to it); with no page asked for, a person with one project lands on it and anyone else on their list. A second photographer's invite opens the shared project. The questionnaire's thank-you, opened from a project's link, goes back to that project when the answers went to it (`/api/questionnaire` says whether they did, never which project they went to otherwise). Julian is emailed when a client edits their details, **starts a project**, or **uploads a file**, each with a link to the project's page or tab (`notifyOwnerOfPortal` in `src/lib/email/notify.ts`, the one sender for all three, muted with `NOTIFY_CLIENT_EDITS=false`, fire-and-forget at `level: "warning"`).

**View as client** on the admin project page (`/admin/projects/[id]/client`) shows the project as its client sees it, from the client's own projection and the same view, read-only, with a banner: no message box, edit form, upload or questionnaire action, and the next step keeps only its links out of the site (the client's paperwork and galleries, the call to book, the review page), which do nothing until they're filled in there.

**Second-photographer access** lets Julian grant a non-owner read-only view of a single project. Each project carries a `collaborators` list (and a GIN-indexed `collaborator_emails` array for the reverse lookup); a "Second photographer access" panel on the admin project page adds a collaborator by email — with an optional one-click invite email — or revokes one. The magic-link gate (`emailHasPortalAccess`) issues links to owners *and* collaborators, so a second shooter signs in passwordlessly like anyone else; their dashboard shows shared projects under a separate "Shared with you" group, and the project page renders a read-only variant: a "Shared with you" banner, the call sheet, their links and files, then the shoot planning answers under "Planning details". A second photographer's read leaves out the money and the paperwork: no budget, package or payment method, no proposal, contract, invoice, highlights or gallery link, and no message thread. The planning answers they see are filtered by the service's own questionnaire (`shootAnswers`): fields marked `booking` there (the package chosen, add-ons, bundle interest, booked or still deciding) and any key the questionnaire doesn't know are left out. The answers still describe the coverage, so this withholds what the client chose, not every clue to the tier. They see the timeline, moodboards and general files. Crucially, **writes stay owner-only by construction**: read access flows through a separate `getProjectForViewer` / `listPortalProjects` path, while every mutation route keeps the owner-only `getProjectForEmail` gate, so a collaborator can never reach an edit. Revocation is immediate (access is re-checked per request), and the columns are migration-added behind their own degrade-gracefully guard. Decisions baked in: read-only, the shoot's details without its money or paperwork, optional invite per grant. On the project page a second photographer gets a **call sheet** in place of the client's next step: when (the date and any other dates), who (the client and partner, the guest count), Julian as the day-of contact, where (the locations) and Julian's timeline for the day (a client's draft stays with their files), then the planning answers about the shoot; never the thread, the plan, the money or the paperwork. Their stage tracker, on the page and on their dashboard card, leaves out the sales steps (the call, the proposal) and how the booking stands (`shootStage`): before the booking there is no tracker and the badge reads "In progress" ("Closed" once a project closed before its booking).

The shoot **Plan** (`plan_summary`) is Julian's to author, and the client sees it read-only. Client questions and Julian's answers live on the project's message thread (see "Client message threads"); the old `client_notes` / `client_notes_reply` columns are copied onto threads by `supabase/schema.sql` and no longer read.

Each project's detail view also surfaces a **prefilled link into the matching planning questionnaire** (`getQuestionnaire(serviceType)`), carrying over name/email/phone/partner/date/guests — so a client who only inquired can flow into the full questionnaire, which attaches back to the same project (matched by email + service) and populates it further. Portal links are surfaced at every relevant touchpoint: the inquiry and questionnaire thank-you panels, the footer's "For clients" list, and the `/client` galleries page. The `/client` page itself leads with the Pic-Time embed (given a little more height) and closes with the "Galleries & project portal" access callout below the reviews, so the gallery is the first thing a returning client sees.

## Owner admin dashboard

An owner-only dashboard at `/admin`, gated by a magic link to `ADMIN_EMAIL` (the same `jose` mechanism as the client portal, with a separate session cookie + purpose; the allowlist is re-checked on every verify, so dropping an address revokes access even on an unexpired token). The Proxy (`src/proxy.ts`) gates `/admin/*` alongside `/portal/*`. The login form is shared with the portal (`PortalLoginForm`, parameterized by endpoint).

`/admin/projects` is the board (see "The Today list and the board" below), and `/admin/projects/[id]` is the project page (see "The project page" below): a header with where the project stands and what's next, over tabs for the overview, the call, messages, links and files, and the details. The details form writes through `/api/admin/update` and carries no status: the header's status select does, and each change adds an entry to the activity log. The **Links & files** tab lists every entry on the project and adds a link or an uploaded file by kind, removes one, marks an invoice paid or unpaid, and offers "Tell the client" on the entry a Compose template would carry, the current link of that kind (it opens Compose on that template carrying that entry's link, through the same `ComposeLink` that the assessment and the next step use; the same entry's link again shows an email left unsent there) (the same route takes these as one change per request, and `/api/portal/upload` accepts the owner's session for the file). A **bundle control** links or unlinks this client's related projects (shown when the person has two or more, writing through `/api/admin/bundle`), and the planning questionnaire renders through the **same collapsible callout the client sees**: collapsed by default, expanding to a section-grouped read-out of label/value rows resolved from the questionnaire schema via `buildAnswerGroups`, with the raw JSON behind its own disclosure rather than dumped on the page. A project can also be **permanently deleted** from a type-to-confirm danger zone (`/api/admin/delete-project` → `deleteClient`). The edit form is **typed to prevent drift**: the service is a dropdown of the catalog's slugs, the package is a dropdown scoped to the selected service's tiers (and clears when the service changes, so the two can never contradict), the event date uses a date picker, and only genuinely free-form fields (name, partner, plan, budget) stay as text; a legacy date that predates the picker degrades to a text field so its value is never dropped. This replaces the Supabase Table Editor for day-to-day management; the table editor remains for complex JSONB edits. The nav's other tabs are **Content** and **Links** (see "Content and links" below). Admin reads use the full row; `listClients` / `getClientFull` / `updateClientAdmin` live alongside the client helpers in `src/lib/clients.ts`. `/admin` is disallowed in `robots.ts`.

Editing a project, changing its status, and adding a link **never email the client**: telling a client something is always a Compose email, so it lands on the project's thread. The reciprocal "a client edited their details" email to Julian is on by default and muted with `NOTIFY_CLIENT_EDITS=false`. That send is fire-and-forget via Resend (`level: "warning"` to Sentry) and no-ops when Resend is unconfigured.

The Details tab's **About this project** card renders stored values as friendly text rather than raw data: the project's **source** reads as words ("Inquiry form", "Questionnaire", "Added manually", "Started in the portal"), and **Created / Last updated** read as "June 7, 2026 · 3 days ago", dates pinned to the studio timezone so a late-evening record doesn't display as the next day.

Every project also carries a **compose-email** panel, on its Messages tab, that turns the communication pipeline into one-click drafts. A stage-grouped picker (`<optgroup>` per pipeline stage) offers starter templates spanning the whole arc — from the first inquiry reply, a "not available" off-ramp, the discovery-call invite and the recap and proposal after the call, through a proposal without a call and its follow-up, the contract and retainer, payment reminders and the booking welcome, planning kickoff and questionnaire nudges, the day-of timeline and week-of note, post-shoot thank-you and sneak peek, gallery delivery and prints/albums, to the review and referral asks, anniversary, a cooled-lead re-engagement, and a gracious **booked-elsewhere** goodbye for a prospect who picked another photographer (`src/lib/email/email-pipeline.ts`) — each prefilling from the project: first name, display name, service noun, formatted event date, venue, the portal, booking and prefilled questionnaire links, the discovery-call booking link and the review link from site settings, the project's own proposal, contract, invoice (with its due date), timeline, highlights and gallery links, the package with its price and inclusions, the service's sample gallery, retainer and the date hold, and the payment method with its how-to-pay line (`emailTokens`, which reads every link from `projectLinks()`). The token names are defined once (`EMAIL_TOKENS`), the token builder must fill each of them, and a spec fails on a template that uses any other. Templates link rather than "attach": an email from the site carries no attachments. Tokens without a value, and free-form `[bracket]` prompts, are left visible so the gaps to fill are obvious before sending. The owner edits freely, then **Send** delivers the message to the client through the shared branded layout (a `PipelineEmailTemplate` that splits the body into paragraphs and auto-links any URLs) via `/api/admin/send-email`, logging the send on the project's thread; or **Copy** drops a subject + body onto the clipboard to paste into his own mail client. The recipient is always resolved server-side from the project id — never trusted from the compose form — and the route no-ops (`sent: false`) when the project has no email on file or Resend is unconfigured. The booked-elsewhere template pairs with a new terminal **`declined`** status — a prospect who chose another photographer, kept distinct from a revivable `lost` lead — which the board files under Closed and the Today list leaves alone (beyond a follow-up).

**Sending a template moves the project on.** Each template says what sending it does (`advancesTo`, `closesAs`, `followUp`, `holdsDate` in `email-pipeline.ts`), and `/api/admin/send-email`, told which template the email started from, applies it once the email has gone: the inquiry reply and the call invite move a lead to Responded and set a follow-up three days out; the recap after the call and a proposal without one move it to Proposal sent, hold the date for the service's hold days (unless a hold is already running) and set a follow-up six days out; the contract-and-retainer email moves it to Booked and the booking welcome to Contract signed, clearing a follow-up an earlier stage set (one set by hand, or by a later stage, stays, `settlesFollowUp`); the planning, timeline, sneak-peek, delivery and review emails move it to their stage, and the post-shoot thank-you moves it to Editing; the review request sets an anniversary follow-up 11 months after the event; and the "not available" and booked-elsewhere goodbyes close it as Archived or Declined, clearing its follow-up and hold. A status only moves forward and a closed project stays closed until reopened by hand; a follow-up that would land in the past isn't set. The rules are one pure planner (`planSendEffects` in `src/lib/email/send-effects.ts`) that the route, Compose, the AI drafter and a spec share. The hold an email names is the one running, or the one that template would start (`holdUntilFor`), so a follow-up never promises a hold nobody set. The panel says before sending what the chosen template would do to this project ("Sending this moves the project to Proposal sent, holds the date until December 2, 2026 and sets a follow-up for December 1, 2026."), and the confirmation says what moved. Each step is applied on its own; one that fails is reported at `level: "warning"` with `stage: "advance"` and named under the confirmation, without counting the send as failed or hiding the steps that worked. The next follow-up shows in the project's header and a running hold on its Overview, and a running hold on the client's portal page; a hold stops showing once the date is being reserved. Closing a project by hand (the status in the project's header) clears its follow-up and hold too. Booking terms are read from the whole service catalog, so a service hidden from the public site keeps its terms for existing projects (`getAnyService`). A package price carries its note ("$125, per person · minimum 5 people"), and the timeline link an email sends is Julian's own, never a client's upload. The Content page's Emails tab states each template's rule without a project (`templateEffectsLine`), beside the line Compose shows for one (`planEffectsLine`), both in `send-effects.ts`.

While the agreement and retainer are out (`booked`), the client's portal reads "Reserving your date" and its stage tracker sits there; the next step says the contract is on its way until Julian adds it, then asks them to sign and pay, then says the retainer is in once an invoice is paid. "Booked" follows when the booking welcome goes out (or the status is set to Contract signed by hand).

## Discovery calls

The project page's **Call** tab (`?tab=call`, drawn with the shared `SubNav`, which takes the active tab for addresses that share a pathname) is what Julian reads from on a discovery call with a prospect, and the owner's new-inquiry email links straight to it ("Prep for the call").

**Guides per kind of shoot live in code**, `src/lib/discovery-guides.ts`, built on Julian's own wedding call guide. One shared framework (before the call, the warm open, about me and how I work, investment and expectations, positioning, the close, after the call) wraps three sections that depend on the kind of shoot: getting to know them, the shoot or event, and their photography priorities. Services fall into six families: couples (weddings, wedding films, engagements and couples), celebrations (cultural milestones, family celebrations), family (maternity, newborn, family portraits, pets), individual (portraits, graduation, modeling), business (headshots, brand and commercial, real estate) and live events (corporate and community events, concerts and performances). Each family has its own opener (a business call opens without congratulations) and "tie it back" line. A question that fits only some services in a family says so ("For maternity or a newborn, when is the baby due...", "For a graduation, will your cap and gown..."). Wedding films add a section about the film and drop the question about wanting one; engagement sessions swap the wedding-day questions about the couple, the day and their priorities for the session's, and open without assuming a wedding is being planned (a per-service opener). A project with no service yet, or one the catalog doesn't know, gets a general **Discovery** guide with no wedding or business wording, which asks for the service to be set before the collections can be listed. The stored service is free text, so lookups only read the catalog's own keys. Questions carry stable ids, unique within their section, and answers are saved under `"<section>.<question>"`; a spec checks every service has a guide with unique keys.

**What needs no AI** sits at the top: the facts in one line (date, venue, guests, budget, how they found Julian, then email and phone), the saved assessment's verdict as a badge when it's current, a **date check** naming any project booked on the same date or a lead holding it ("Booked: ...", "Held for ... until ..."), with the same client's own projects on that date named apart rather than as a clash, and the service's collections (`ServiceCollections`, shared with the Content page: packages and inclusions, add-ons, retainer, date hold, turnaround and sample gallery). Each section folds open; the family's three start open. Every question has an answer box, **My notes** sits beside them (sticky on a wide screen), and everything typed **autosaves** a second and a half after typing stops, when a box loses focus and when the tab is left, batched into one request to `/api/admin/update` (`call: { answers, asked, notes, base, writer, seq }`). Each answer is saved with the question it was typed under. The save status ("Saved 3:42 PM", "Not saved yet. Trying again.") sits under My notes on a wide screen and stays pinned at the top on a narrow one, all the way down to the notes. A failed save (the network, a 5xx) keeps what's pending and retries every five seconds; a refused one waits for the next change instead of retrying forever, and the boxes stop at the lengths the route accepts (`CALL_ANSWER_MAX`, `CALL_NOTES_MAX` in `src/lib/calls.ts`). What's typed is kept per project for as long as the browser tab is open (`call-draft.ts`), so coming back to the tab, by link or by the back button, shows the latest notes rather than the page's first copy. A `merge_call` Postgres function merges each save into `client_records.calls` (keyed by call, `discovery`) answer by answer, so two saves landing together both keep what they wrote, without touching `updated_at`. Each autosave names the save it was typed against, the open copy it came from (a random id per copy, stored as `savedBy`) and that copy's count of saves (`savedSeq`), and `merge_call` refuses it (409) when another copy saved the notes since, so a copy left open in another window can't overwrite newer notes; that window says so and stops saving. A copy retrying its own save, one whose reply was lost, isn't taken for another, and a first try that reaches the database after its own retry is refused rather than taken as newer. Emptying an answer listed under another guide keeps its box until the page is next opened, so it can be retyped. Repeated or blank tailored questions are dropped, one box per question.

**Tailored to the client**, on demand: "Tailor to this client" (`/api/admin/ai`, kind `call-guide`) reads the internal-tier facts, the saved assessment, the inquiry, the latest six messages and the questionnaire answers (with email addresses, links and phone numbers taken out), the service's collections and the guide's own sections, and returns what to know at a glance, the angle to take, six to eight questions of their own (each with an answer box, saved under a key made from the question, `tailored.<hash>`, so tailoring again never moves an answer onto a different question), a note marked **Internal, don't read aloud**, and a tailored opening line for sections of the guide. The thread it reads, and the fingerprint it's saved with in `ai_results` (the inquiry, the newest message and the questionnaire, so new messages or answers mark it out of date), count only the conversation: replies and portal messages received, and what Julian wrote that went out, by email or in the portal (`isConversation` in `src/lib/messages.ts`, matching the `client_last_contact` view), never bounces, held-back out-of-office replies or the site's automatic emails. Answers to questions no longer on screen, from an earlier tailoring or another service's guide, stay listed under "Answered under another guide", and the summary reads them.

**After the call**, "Summarize the call" (kind `call-summary`) turns the answers and notes into five editable parts: background, event details, photography priorities, budget and logistics, and Julian's action items. It also suggests updates to the project (guest count, date, venue, package, the package only when the service offers it), each applied only when he presses **Accept**. Summarize saves the notes on screen first, and says so when they couldn't be saved (and why, when they've stopped saving), when there's nothing to summarize yet, or when the AI's answer couldn't be used. An accepted venue names the first location when it has only an address, and otherwise goes first as a new place, with the old one kept below to edit. **Save summary** stores it (`callSummary` on `/api/admin/update`). The first save moves a lead to In conversation and, unless the proposal has gone out or the project is closed, sets a follow-up for the next day to send the recap, then marks the call held, so a save that fails partway is redone in full the next time; saving it again changes only the summary, keeping the held date and whatever follow-up is set. **Write the recap** saves an edited summary first and refreshes the page, so going Back shows the saved summary rather than the browser's earlier copy, then opens Compose on the recap and proposal template, and the AI draft of that email reads the summary's first three parts (what the client said) but never the budget notes or the to-do list. `Panel` gains a `surface` prop for a box set inside another, used by the internal note.

## The Today list and the board

`/admin/projects` opens with **Today**: what needs the owner now, worked out from every project by rules rather than AI (`todayRows` in `src/lib/today.ts`, pure, so the board, the specs and a morning email can share it). Days are the studio's: a message sent in the evening counts on the day it was sent in Eastern time (`studioDayOf` in `src/lib/field-format.ts`, which `studioToday` is built on). A row shows for:

- a **follow-up** that's due or overdue (any project, a closed lead's last check-in included);
- a **client who wrote last** and hasn't had an answer, from the `client_last_contact` view (the client's newest received message against the owner's newest one that went out, by email or as a reply posted in the portal);
- a **new inquiry** nobody has answered, at any age, due from the day it arrived ("New inquiry 9 days ago, not answered yet");
- a **date hold** that ran out before the lead booked;
- an **unpaid invoice** due within a week, or overdue (going overdue is a row of its own, so one marked handled while it was coming due shows again once it's late);
- a **booked shoot** two weeks out or less with no questionnaire back (for services that have one; an older free-text date counts when it names one day, "12/05/2026" or "Dec 5, 2026", read by the same `eventDay` that `daysUntil` and the edit form use, while a range, a season, a month alone or a hedge such as "TBD June 6, 2027" reads as no date);
- a project **still in editing** past its service's turnaround days (set in Studio).

Each row says why it's there, offers one thing to do (open the project, draft the reply, or open Compose on the follow-up, payment or questionnaire reminder), and has **Mark handled** and **Snooze** (three days). On a follow-up row, Mark handled clears the follow-up and its note and Snooze moves it, keeping the note, both only while it's still the follow-up the row showed: the request names it (`followUp.expect`), and one changed since the page loaded is left alone (409) and the list reloads. On any other row they're saved on the project (`today_dismissed`, keyed by the rule and what set it off, through a `dismiss_today` Postgres function the service role alone may run), so the same rule firing for something new, a later message or a new hold, shows again. Rows are ordered by the day each fell due, so the longest-waiting come first. Wherever an event date is shown (the client portal's dashboard and project page, the `{{eventDate}}` email token, the AI's project facts, the Call tab, the board's cards and Ask results), one day is written out and anything else shows as it was typed (`formatEventDate`), never as a guessed day; a project's automatic name carries the day only when there is one, and the email token leaves its `[eventDate]` marker to fill in when the text names no year ("TBD"); the Ask search reads an event's month and year with `eventMonthYear` ("Fall 2027" counts for 2027) and is told the studio's today.

Below it, a quick-add for a project booked through Square or over the phone, and **one search box**: **Search** narrows the board to projects holding every word typed, in a name, email, service (its slug or title) or project name, with a service dropdown; **Ask**, when AI is set up, reads the words as a plain-English question. The box follows the address, so Back, Forward and Clear show the search the board shows; a Search can't start while an Ask is out, and an Ask answered after the search changed is dropped. The board groups projects into **phases**: Leads, Booked (soonest shoot first), In production, Delivered, and Closed, folded away. Each card shows its stage, service and date, the next follow-up or a running date hold, and when each side last wrote, counted in the studio's days as Today counts them ("Client wrote 2 days ago, you 5 days ago", or "You wrote today"); `listClients` reads the last-contact view in one extra query.

## The project page

A Compose hand-off (`?compose=<template>`) with no tab opens Messages, so every "Draft a reply", "Tell the client" and next-step link lands on Compose, which brings itself into view when it opens from another tab; a reply to the inquiry shows what they wrote and its saved assessment above it.

Every link to the inquiry reply is one address (`draftReplyHref`, which no longer carries the assessment's time), so the reply comes back from any of them, and saving the call summary or accepting one of its updates drops a recap left unsent, so the recap opens from the new facts. Beside the inquiry reply, the assessment doesn't offer to open Compose again. **Overview** shows what matters at the stage. A closed project shows the stage it stopped at. A booked project shows a checklist toward the shoot (contract added, retainer paid, how they'll pay, questionnaire back, shoot date set, timeline details sent) beside the questionnaire and its prep brief; after the shoot, a checklist toward delivery (highlights, the gallery, the gallery email, invoices paid, a review asked for). **The activity log** (`status_history`) lists, newest first, each move in the pipeline with what moved it and the owner's dated notes, with a box to add one (`note` on `/api/admin/update`, appended by an `add_activity` Postgres function in one statement). Every status move is one statement too (`set_status`: it moves the project only while it still has the status it was read as, adds the entry to the log, and clears the follow-up and hold when it closes the project), so a note and a move landing together are both kept; both functions are the service role's alone, and the update route accepts only known statuses. It replaces the private notes box on the form: notes kept there became the log's first entry, marked "Earlier notes" and undated, by a backfill in `supabase/schema.sql` that copies a box's text once, and on a later run replaces that copy with the box's last edit. It also replaces the board's quick-update control and its `/api/admin/quick-log` route, and the rail's status history and follow-up lines.

## Project bundles

Two or more of one person's projects can be linked into a **bundle** — a wedding and its engagement session, a maternity and newborn pairing, or any grouping Julian sets up. A bundle is a shared `bundle_id` across the linked rows plus a denormalized `bundle_label` (the display name), so the relationship reads from any one project without a join. Both sides can manage it: the client links their own projects from the portal menu (`PortalBundles` → `/api/portal/bundle`), and Julian links a client's projects from the admin project page (the same component, pointed at `/api/admin/bundle`). The two write paths share one invariant — a bundle can never span two people. The client path drops any project id the signed-in email doesn't own; the admin path requires every selected project to resolve to a single email. Linking needs two or more projects and a label; unlinking clears the pair on one project.

The link is **visible by text, color, and grouping**. On the portal menu, bundled projects leave the per-category grid and render together in their own accent-bordered block headed by the `↔` glyph, the bundle label, and a "Bundle" tag; their cards carry an accent border. On both admin surfaces — the projects overview and the project detail page — a linked project shows an `↔ {label}` badge. The bundle control itself surfaces any existing bundles (label + member projects) in its collapsed header, so the grouping is visible before the panel is opened to add more or unlink. The interface matches the rest of the site: the same card shells, accent variables, and serif headings as the services / galleries menus.

## AI-assisted drafting

Generative actions use the shared `Button` (secondary variant) with plain verb labels and its loading state; there is no separate AI button style. Each AI feature does one job: client email is drafted only by the compose panel's "Draft with AI" (`/api/admin/draft-email`). The assessment (fit, urgency, summary, key details) carries a "Draft a reply from this" link that opens the compose panel on the inquiry-reply template (`?compose=inquiry-reply`, built by `draftReplyHref`); the page steers that draft from the assessment saved on the project (`triageSteer`), so no client detail rides in the address. The project's next step opens its template the same way (`?compose=<template>`), and a link's "Tell the client" adds `&doc=<entry id>`. The panels share one `useAiAction` hook for the request, result and error; the assessment and brief panels keep their result when a run comes back empty, and the others clear it.

The compose-email panel on a project gains an admin-only **"Draft with AI"** button that turns a pipeline template + the project's real context into a personalized, on-brand draft — which Julian reviews and edits before sending (the AI never sends; it only fills the editable subject/body). An optional one-line steer ("mention the rain backup", "warmer tone") tunes the result, which lands under an "AI draft — review before sending" note.

A provider abstraction in `src/lib/ai/ai.ts` fronts any OpenAI-compatible chat-completions API with a single `generateText({ system, prompt })`. The default is **Groq** — free, fast, and (per their policy) non-training, which is why it's the pick for prompts carrying client PII — and it's swappable to any OpenAI-compatible endpoint via `AI_BASE_URL` — including Vercel's AI Gateway as a documented target (`.env.example` carries the base URL, slug format, and the caveat that enforced zero-data-retention routing is Pro-plan-gated, so direct Groq stays the default for client-data prompts). The whole module no-ops (returns null) when `GROQ_API_KEY` is unset, so the compose panel simply omits the AI button and stays a manual editor — the same optional-by-env posture as Resend and Twilio. The key is server-only, never `NEXT_PUBLIC_`.

Models are not hard-coded. `src/lib/ai/models.ts` lists the provider's live catalogue, keeps chat models with enough context, ranks them by family, and test-calls a model before adopting it; the fallback comes from a different family, and the vision model must pass an image probe. `AI_MODEL`, `AI_FALLBACK_MODEL` and `AI_VISION_MODEL` are optional pins, honoured while still served. The choice is stored in `app_settings`, refreshed by the daily cron, and re-made at once when a call hits a retired model (primary, then fallback, then a fresh pick). The owner gets one email when the choice changes. Text and vision share one request path with retries on rate limits and 5xx; a model still rate-limiting after the retries hands the call to the fallback, whose family has its own limits on Groq's free tier. Being busy isn't a reason to re-choose the models (a retired one still is), and the call fails only when every model is busy.

The drafter learns Julian's voice: `src/lib/ai/voice-samples.ts` takes his three most recent substantial emails to other clients (composed here, answered from Gmail, or filed from Gmail), redacts names on those projects, addresses, links and phone numbers, and passes them as style examples the model may not take facts from. An AI draft edited before sending is stored as sent, so edits shape later drafts.

`/api/admin/draft-email` (admin-gated, per-IP rate-limited, Sentry-instrumented) loads the project server-side and sends the model only the minimal, client-appropriate facts a draft needs — name, service, stage, date, venue, package, guest count, plan summary, the project's portal, booking and questionnaire links, the links Julian has added (proposal, contract, invoice, highlights, gallery), and how the client is paying — never the owner's notes (the activity log) or budget, never the client's email or phone, and never PII trusted from the request body. The questionnaire link a client receives is prefilled with their contact details, so the prompt carries the same form's address without them and the real link is put back into the returned draft. A reusable brand-voice system prompt (`src/lib/ai/ai-voice.ts`) establishes Julian's persona and the non-negotiable rules — write as Julian, use only the supplied facts, leave a `[bracket]` placeholder rather than invent a missing detail — so a draft reads like him and can't fabricate a date or price. The model returns a `Subject:`/body pair parsed straight into the editable fields, falling back to the static filled template if the provider is unreachable. This was the first consumer of the shared `ai.ts`.

The AI tools that work on one project sit behind **one route, `/api/admin/ai`**, chosen by `kind` (admin-gated, per-IP rate-limited, Sentry-instrumented with the kind as a tag). Each builds its prompt from **one context builder**, `projectFacts()` in `src/lib/ai/project-context.ts`, at the tier its output reaches: the **client** tier (service, people, date and venue, guests, package, stage, plan) for anything a client will read, and the **internal** tier, which adds the budget, how they found Julian, where the project came from and its status, for what only Julian reads. Neither tier carries the client's email or phone, and the client tier never the budget, referral or the owner's notes. The email drafter's facts come from the client tier too. The tools live in `src/lib/ai/project-ai.ts`:

- **`triage`** assesses the project's inquiry: a one-line summary, a fit verdict (good / maybe / poor) with a reason, an urgency read (high / medium / low, weighing event-date proximity), and the key details worth saving. The prompt, schema and call are the module the inquiry route uses on arrival (`src/lib/ai/assess-inquiry.ts`); the shape and labels live in `src/lib/triage.ts`, shared by the panel and the email.
- **`shoot-brief`** turns a submitted planning questionnaire into something useful on the day: the snapshot's field ids resolved to their labels and grouped by section (`buildAnswerDigest` in `src/lib/questionnaire-digest.ts`), then a one-line headline plus sections (timeline, key people, must-have shots, locations, special moments, logistics, style), each a few short bullets, with gaps flagged as `[confirm with client]` rather than invented.
- **`call-guide`** and **`call-summary`** fit the discovery-call guide to the client and write up the call afterwards (see "Discovery calls").
- **`plan-summary`** drafts the client-facing plan summary for the edit form's **"Draft with AI"** button: a short, warm overview in Julian's voice from the client tier and the client's own answers, dropped into the field for him to refine and save (it confirms before overwriting).

Every answer the model must give as JSON goes through a tolerant extractor (`extractJsonObject`) and a zod schema, with `.catch()` fallbacks on enums; an unusable answer is reported at warning (`stage: "parse"`) and asks for a retry rather than showing a broken card. **The assessment and the shoot brief are saved on the project** (`ai_results jsonb`, keyed by kind, each with its result and when it was made), written one kind at a time by a `save_ai_result` Postgres function so two saves can't overwrite each other, and without touching `updated_at`. Each saved result carries a fingerprint of what it was made from (the inquiry message, the questionnaire answers), so a client resubmitting their answers marks the brief as out of date, and an assessment that no longer matches the inquiry is flagged and no longer steers the reply. The project page shows what's saved ("Assessed November 25, 2026 at 3:04 PM") and never calls the AI on view; "Assess again" and "Re-generate brief" run it on demand and replace the saved one. A saved result still shows when AI isn't configured, without the button. The route answers `generated: false` without a key, a project or anything to read; every failure on it is tagged with the kind, and a result that couldn't be saved is reported on its own (`stage: "save"`) rather than shown as saved. The questionnaire answers the tools read leave out the client's contact details. The three single-purpose routes it replaced (`/api/admin/triage`, `/api/admin/prep-brief`, `/api/admin/draft-plan`) are gone.

Together these surfaces (email drafting, the project AI tools: assessment, shoot brief, plan summary, call guide and call summary, and the Ask search) make up the AI admin layer, all on the single `ai.ts` provider abstraction (Groq by default, any OpenAI-compatible endpoint by env). A project's next step is worked out by rules, not AI (see "The project page"); the on-demand "Suggest next step" button and its `/api/admin/next-action` route are gone.

The **website copy drafter** extends the same `ai.ts` beyond the client pipeline, on the Content page's **Website copy** tab (`/admin/content?tab=copy`). It drafts text only and **never publishes**: Julian reviews and saves in Sanity Studio. One route, `/api/admin/draft-copy`, takes either kind of draft (`kind: "journal"`, or `"service"` / `"portfolio"`), and both prompts carry the site's writing rules (the banned phrases and no em dashes, from `ai-voice.ts` and `copy-rules.json`).

A **journal post** (kind `journal`) is drafted from a topic or brief, with an optional post type (recap, educational, personal essay, seasonal), in Julian's voice: title, excerpt, body, and suggested tags, each copyable. It's deliberately **topic-driven and never reads private client data** (the journal is public), the prompt is told not to fabricate names / prices / stats (it leaves `[brackets]` instead), and the output maps to the journal post's draftable fields — the schema-required cover image + publish date stay Julian's to add in Studio (an AI can't supply a photo).

**Page copy** (kind `service` or `portfolio`) drafts or tightens a page's marketing copy: pick a page + a mode (tighten the current copy / rewrite fresh / draft from scratch) with an optional angle, and it returns an improved tagline, description, and intro — copyable — built from **the copy that's currently live** (read server-side via `getService` / `getPortfolio`). Same guardrails: uses only the live facts, never invents prices/claims, no-ops without a key or for a page the site doesn't show. Changing what to draft clears the draft on screen, and a reply to a request made before the change is dropped (`useAiAction`'s `reset`).

A shared `CopyField` backs every Copy action, in the drafter and on the Links page, and its button names what it copies for screen readers ("Copy Title").

**Natural-language project search** is the board search box's **Ask** button (`/api/admin/search`): a query like "weddings in June with no contract yet" is sent to the AI, which returns a **structured filter spec** — statuses, service, free text, event month/year, an upcoming-days window, and gallery / questionnaire flags — that the route then applies to the client list server-side, returning the matching projects with a note on how the query was interpreted. The semantic interpretation (e.g. "no contract yet" → the set of pre-contract statuses, "June" → the right month/year relative to today) lives in the model; the route only applies concrete, validated filters, so a malformed spec can't run arbitrary logic. It reuses the existing `listClients` read, returns only board-level fields (never the activity log), **short-circuits to no results on an empty store without calling the provider**, and no-ops without a key. **Search**, in the same box, narrows the board by keyword and service instead (`?q=`, `?service=`).

**Portfolio image alt text** is generated two ways, both backed by a new vision capability in `src/lib/ai/ai.ts` — `describeImage({ system, prompt, imageDataUrl })`, the multimodal sibling of `generateText`, using a separate `AI_VISION_MODEL` (default `meta-llama/llama-4-scout-17b-16e-instruct`) so the text default is untouched. At **import time**, `npm run import-photos --alt` describes each new or still-placeholder image inline (the script makes the same Groq vision call by `fetch`, since a Node `.mjs` can't import the TS module); without the flag or a key, images keep the neutral `"<slug> photograph N"` placeholder. The importer also now **preserves** any non-placeholder alt already in the manifest across re-imports, so AI descriptions and hand edits are no longer wiped on the next run. A per-image **admin tool** (Content → Website copy → *Portfolio image alt text*) lists a gallery's photos, generates one image's alt on demand (`/api/admin/draft-alt`, which validates the `src` belongs to the named gallery, fetches it server-side, and describes it — never publishing), and **persists** a reviewed override (`/api/admin/save-alt`). Overrides live in a small Supabase `portfolio_image_alt` table (`src` → `alt`), read through `src/lib/portfolio-alt.ts` — a self-contained, service-role module that degrades to `{}` when Supabase is unset, deliberately separate from the CRM store. The portfolio detail page overlays these overrides onto the manifest baseline at render, so a saved description wins over the import-time alt and survives the next import. The whole feature is optional-by-env at every layer: no key → placeholder alt; no Supabase → manifest alt; both absent → galleries still render.

The tool also covers **Studio-uploaded galleries**: because Sanity gallery images resolve into the same `p.images`, they show up in the picker automatically, and `draft-alt` fetches absolute `cdn.sanity.io` URLs directly (site-relative manifest paths still get the origin prefixed). A saved override wins over the image's own Studio `alt` at render through the same overlay — so alt for a batch uploaded in Studio can be generated + reviewed here rather than typed per photo, with no runtime Sanity write token.

**Public booking concierge & FAQ** complete the AI suite with its only visitor-facing surface. A new `/faq` page consolidates every question into one searchable, filterable directory — free-text search over question + answer, a collection filter (a general bucket plus each umbrella) with a per-service sub-filter, native `<details>` accordions grouped by service, and a consolidated `FAQPage` JSON-LD block. The FAQ set is a single shared source (`src/lib/faq.ts`): a curated, evergreen general set owned in code plus every visible service's `faqs[]`, each tagged with its umbrella and service so the directory can map and filter them. That same source grounds a site-wide **concierge chat** — a floating "Ask" widget (and a docked panel on `/faq`) that fields questions about services, pricing, and booking and steers toward the inquiry form. It's multi-turn (`generateText` gained an additive `messages` transcript option) and grounded only in public catalog content assembled by `src/lib/ai/concierge-kb.ts` — site settings, the condensed service catalog with prices, the shared FAQ set, and the about bio. The `POST /api/concierge` route mirrors the public inquiry pattern (per-IP rate limit, honeypot, bounded message size + history) and **never imports the client/CRM store**, so no private data can reach the model; its system prompt forbids inventing prices or availability, keeps scope to Julian's photography, ignores instructions embedded in visitor messages, and hands booking actions to the inquiry form. The model has no tools and its reply renders as plain text — nothing is executed. Everything degrades by env: the directory is always available, while the chat appears only when `GROQ_API_KEY` is set (otherwise a static pointer to the FAQ and inquiry form). The widget self-suppresses on `/faq` and on the studio / admin / portal chrome.

**Client-side writing assistant** turns the same `ai.ts` toward the people filling the forms, not just the admin reviewing them. The three open-text moments in the funnel — the inquiry's "Tell me about your vision," every questionnaire `textarea`, and the portal's "Notes / questions for me" box — share one `AssistedTextarea` component with an opt-in **"Help me write this"** affordance. It opens a two-box panel: the client jots rough notes (even keywords), the assistant shapes them into a clear, first-person draft in a _separate, editable_ box, and the field itself is touched only if they pick **Use this** — so they can refine their notes and re-draft, edit the suggestion directly, or cancel back to their own words. Each surface feeds the draft the facts already known this session — the client's other answers so far, or (in the portal) the project's service / date / status — so it reads as theirs and stays consistent, while the model is forbidden from inventing any specific (name, date, venue, price) not present in those facts. A single `POST /api/assist/draft` route mirrors the concierge's public posture (per-IP rate limit, honeypot, bounded sizes) and is **stateless** — it imports no catalog or CRM data and persists nothing, so the client PII it shapes only passes through the non-training provider. It stays a writing assistant, never the photographer: the prompt won't quote offerings or answer on Julian's behalf, treats the notes + context as material rather than instructions, and returns the draft plus an optional one-line `tip` nudging a detail worth adding when the notes are thin. The affordance appears only when `GROQ_API_KEY` is set (threaded to the client as a server-evaluated flag, since the key is server-only); without it, every field is a plain textarea.


## Client message threads

Every email to or from a client lives on one thread per project (`client_messages`), shown on the admin project page and, minus anything held for review, in the client's portal. All sending goes through `sendEmail()` (`src/lib/email/send.ts`): it reads Resend's result (the SDK returns errors rather than throwing), retries dropped connections, rate limits and 5xx, keeps subjects on one line, always sends a text part, and redirects mail from preview and local builds to the owner. A production deploy without a key fails loudly. The compose panel reports what happened (404 unknown project, 409 no email, 503 not set up, 502 refused with Resend's reason), sends once per version of a message via an idempotency key, and BCCs the owner; update and confirmation emails join the thread without a copy.

Sends on a thread carry the project's reply address, `reply+<token>@` on the inbound subdomain (`RESEND_INBOUND_DOMAIN`), and reply headers that keep mail apps threading. `/api/email/webhook` verifies Resend's signature, updates delivery status (a bounce or spam complaint emails the owner), and files received mail: a client's reply is stored and forwarded to the owner's inbox with the reply address as Reply-To, so answering from Gmail goes back through the site; the owner's own reply is relayed to the client only when DKIM shows it came from the owner's domain, otherwise it is held with a one-click send, which confirms on the spot and marks the held copy "Sent after review"; mail from an unknown address is held and flagged; automatic replies are filed and go nowhere. Every write is idempotent on Resend's ids. A daily check settles messages whose delivery event never arrived. Clients can also write from the portal; collaborators can't see the thread. Past sends can be filed from Resend's log (`npm run messages:backfill`), and mail that only exists in Gmail by forwarding it to the project's `log+<token>@` address, which files it with its original sender and date.

The studio address is julian@julianperezphotography.com (`CONTACT_EMAIL`), routed to the owner's Gmail by Cloudflare Email Routing on the root domain; Resend sends from the `send.` records and receives on its own `in.` subdomain, so the three never collide.

## API routes

JSON routes are declared with `defineRoute()` (`src/lib/api-route.ts`), which does auth (admin, portal or public), the rate limit, JSON and schema parsing, the honeypot, and Sentry reporting with the route's tag, in that order, and answers every failure as `{ error }`. Handlers only do their own work.

## Configuration and safeguards

`src/lib/config.ts` lists every setting the code reads, what goes without it, and whether production needs it. `.env.example` and `docs/configuration.md` are generated from it (`npm run env:docs`); a spec fails when either is stale or when code reads a setting the list doesn't know. A production server logs missing settings at boot, and the admin Links page lists them under Site services, with a one-line pointer on the Projects board (`unfinishedSetup()`, which reads a blank value as unset). `npm run email:check` verifies SPF, DMARC, the Resend domain and its DKIM records, the receiving MX and the webhook, and `--send` proves a real delivery. The daily cron refuses to run in production without `CRON_SECRET`. Questionnaire upload tokens go only to a browser on this site, for a `questionnaires/` path; portal upload tokens need a client's session or the owner's. `noteOwnerOnChange()` emails the owner when an automation's state changes, not every time it runs. Links in emails (sign-in links, invites, the inquiry's Draft a reply) are built by `originOf()` from the address the request reached, never from its `Origin` header: any client can set that, and a forged one would have put another site's address, carrying a live sign-in token, into a real email from this one.

## Testing and CI

The Playwright suite never reaches a real provider. `tests/e2e/support/fake-providers.mjs` stands in for Resend, the AI provider and Twilio, so sends, drafts and sign-in emails run their real code paths; the `fakes` fixture reads what was sent and scripts failures, and the sign-in fixtures read the magic link from the fake inbox. The client store for tests is a separate Supabase project (`.env.test`); each run starts by clearing test records over an hour old, specs create the records they assert on, and store-backed specs skip without it. The cron spec covers the model check against the fake catalogue: the preferred family is chosen, a retired family hands over to another one with a single owner email, and a request whose model was just retired is answered by the fallback. File-scan specs guard the UI kit (`style-system.spec.ts`) and the settings list (`config.spec.ts`). CI (`.github/workflows/ci.yml`) runs lint, typecheck and the suite against a production build on every push and pull request.

## Writing rules

Visible text follows `src/lib/copy-rules.json`: no banned stock phrases, no em dashes, FAQ answers that start with the fact. `scripts/check-copy.mjs` enforces it in `npm run lint`, skipping comments and AI prompts, and the drafting voice tells the model to avoid the same list. The pipeline email templates, service and FAQ copy, questionnaire text and page copy were rewritten to these rules with every fact unchanged.
